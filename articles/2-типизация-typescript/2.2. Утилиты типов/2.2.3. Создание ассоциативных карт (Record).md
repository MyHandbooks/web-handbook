# 2.2.3. Создание ассоциативных карт (Record)

## БЫСТРЫЙ СТАРТ

*   **`Record<K, T>`** — это встроенная утилита типов, которая конструирует тип объекта (ассоциативную карту или словарь), где ключи имеют строго заданный тип `K`, а значения — тип `T`.
*   **Контроль полноты (Exhaustiveness Checking):** Если в качестве ключей `K` выступает Union-тип (объединение строковых литералов), TypeScript принудительно обяжет вас объявить в объекте абсолютно все перечисленные ключи. Пропуск хотя бы одного ключа вызовет ошибку компиляции.
*   **Используйте его для:** создания справочников, таблиц конфигураций пользовательского интерфейса (маппинг статусов на цвета/иконки), динамических кэшей данных или реестров сервисов.
*   **Не используйте его:** для создания ассоциативных карт, где ключами должны выступать сложные объекты. Ключами в `Record` (в силу физики JavaScript) могут быть только типы, приводимые к строкам, числам или символам. Для объектов-ключей используйте встроенный класс `Map`.

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Строго типизированная карта маппинга статусов (Exhaustive Map)
*   **Назначение:** Связывание системных статусов бизнес-логики со специфическими визуальными настройками отображения в интерфейсе с гарантией полноты описания.

```typescript
export type DataState = "pending" | "fulfilled" | "rejected";

export interface StatusConfig {
  displayName: string;
  uiThemeClass: string;
}

// Конструируем строгий словарь, где каждый статус из DataState обязан иметь свою конфигурацию
export const statusRegistry: Record<DataState, StatusConfig> = {
  pending: {
    displayName: "Ожидание обработки",
    uiThemeClass: "theme-accent"
  },
  fulfilled: {
    displayName: "Успешно завершено",
    uiThemeClass: "theme-success"
  },
  rejected: {
    displayName: "Критическая ошибка",
    uiThemeClass: "theme-error"
  }
  // Если мы добавим новый статус в DataState, но не опишем его здесь, TS выдаст ошибку компиляции
};

export function getStatusTheme(state: DataState): string {
  // Благодаря Record доступ к свойству полностью безопасен в рантайме
  return statusRegistry[state].uiThemeClass;
}
```

### Шаблон 2: Динамический кэш/хранилище с неограниченными ключами
*   **Назначение:** Описание типизированного хранилища данных в оперативной памяти (кэша), где ключи генерируются динамически в рантайме.

```typescript
export interface TargetPayload {
  identifier: string;
  serializedData: string;
}

// Ключом может быть любая строка, а значением — строго объект TargetPayload
export type MemoryCacheStore = Record<string, TargetPayload>;

export class InMemoryCacheService {
  // Инициализируем пустое хранилище кэша
  private cache: MemoryCacheStore = {};

  public save(key: string, data: TargetPayload): void {
    this.cache[key] = data; // Запись полностью типобезопасна
  }

  public get(key: string): TargetPayload | undefined {
    // Внимание: TypeScript считает, что по любому ключу лежит TargetPayload. 
    // На самом деле ключа в рантайме может не быть, поэтому явно возвращаем undefined
    return this.cache[key];
  }
}
```

### Шаблон 3: Многоуровневый вложенный Record для конфигураций
*   **Назначение:** Описание сложных вложенных структур данных (например, прав доступа для ролей пользователей в разрезе разделов приложения).

```typescript
export type UserRole = "admin" | "editor" | "viewer";
export type AppSection = "dashboard" | "billing" | "analytics";

export interface PermissionSet {
  canRead: boolean;
  canWrite: boolean;
}

// Двумерная ассоциативная карта: Сначала группируем по Роли, затем внутри по Разделу приложения
export type SecurityMatrix = Record<UserRole, Record<AppSection, PermissionSet>>;

export const securityMatrix: SecurityMatrix = {
  admin: {
    dashboard: { canRead: true, canWrite: true },
    billing: { canRead: true, canWrite: true },
    analytics: { canRead: true, canWrite: true }
  },
  editor: {
    dashboard: { canRead: true, canWrite: true },
    billing: { canRead: true, canWrite: false },
    analytics: { canRead: true, canWrite: false }
  },
  viewer: {
    dashboard: { canRead: true, canWrite: false },
    billing: { canRead: false, canWrite: false },
    analytics: { canRead: true, canWrite: false }
  }
  // Полная проверка структуры со стороны TS защищает от случайного пропуска прав для любой роли
};

export function checkAccess(role: UserRole, section: AppSection, action: keyof PermissionSet): boolean {
  // Двойной индексный доступ полностью валидируется статическим анализатором
  return securityMatrix[role][section][action];
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Внутренний механизм Mapped Types под капотом `Record<K, T>`
Утилита `Record` является сопоставленным типом (Mapped Type) и в стандартной библиотеке TypeScript описывается лаконичной строкой:
```typescript
type Record<K extends keyof any, T> = {
    [P in K]: T;
};
```
*   `K extends keyof any` — ограничение первого обобщенного параметра `K`. Конструкция `keyof any` эквивалентна типу `string | number | symbol`. Это означает, что ключами могут выступать только типы, пригодные для индексации объектов в JavaScript.
*   `[P in K]` — итератор, который последовательно проходит по каждому литералу, входящему в тип `K`.
*   `T` — фиксированный тип значения для каждого из ключей. В отличие от `Pick<T, K>` или `Partial<T>`, утилита `Record` не извлекает исходные типы из существующего объекта, а жестко назначает переданный тип `T` каждому ключу.

### 2. Принцип контроля полноты и защита от деградации справочников
Использование `Record` с Union-типом ключей защищает кодовую базу от критических ошибок при масштабировании приложения:
*   Представьте, что вы добавили новое значение в статус-модель `DataState = "pending" | "fulfilled" | "rejected" | "processing"`.
*   Если конфигурация визуального рендеринга была описана как `statusRegistry: Record<DataState, StatusConfig>`, компилятор немедленно заблокирует сборку проекта, указав, что свойство `"processing"` отсутствует в объекте.
*   Это принуждает разработчика сразу описать логику работы для нового элемента во всех справочниках приложения, не допуская появления "белых пятен" в интерфейсе в рантайме.

### 3. Детальный пошаговый разбор выполнения вложенного шаблона 3
Проследим логику сборки типа `SecurityMatrix = Record<UserRole, Record<AppSection, PermissionSet>>` компилятором:
1.  **Вычисление внутреннего типа (`Record<AppSection, PermissionSet>`):**
    TypeScript трансформирует Union `"dashboard" | "billing" | "analytics"` в объектный тип:
    ```typescript
    type InnerRecord = {
      dashboard: PermissionSet;
      billing: PermissionSet;
      analytics: PermissionSet;
    }
    ```
2.  **Вычисление внешнего типа (`Record<UserRole, InnerRecord>`):**
    TypeScript итерируется по Union `UserRole` (`"admin" | "editor" | "viewer"`) и назначает каждому ключу структуру `InnerRecord`.
3.  **Итоговый тип `SecurityMatrix`:**
    Компилятор формирует строгую двумерную структуру, где каждый узел гарантированно типизирован. Попытка обратиться к `securityMatrix["unknown_role"]` или к `securityMatrix["admin"]["unknown_section"]` моментально завершится синтаксической ошибкой.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Ошибка неопределенности при чтении динамического Record (Иллюзия безопасности)**
    *   *Проблема:* Разработчик объявляет тип кэша как `Record<string, TargetPayload>`, запрашивает элемент по ключу `cache[id]` и сразу обращается к свойству `cache[id].identifier`. В рантайме такого ключа в кэше может не оказаться (он вернет `undefined`), что приведет к падению программы с ошибкой `TypeError: Cannot read properties of undefined`.
    *   *Решение:* Если ключи объекта генерируются динамически, TypeScript по умолчанию считает, что значение по любому ключу всегда существует. Вы должны защитить код, явно добавив `undefined` в тип значений или настроив компилятор с помощью опции `noUncheckedIndexedAccessInIndexSignature` в `tsconfig.json`.

```typescript
// ПЛОХО (Компилятор считает, что payload точно существует, но рантайм вернет undefined)
export function runPayloadUnsafe(id: string, cache: Record<string, TargetPayload>): void {
  const payload = cache[id]; 
  console.log(payload.identifier.toLowerCase()); // ! TypeError в рантайме, если ключа id нет в кэше
}

// ХОРОШО (Явное добавление undefined заставляет выполнить проверку перед использованием)
export type SafeCacheStore = Record<string, TargetPayload | undefined>;

export function runPayloadSafe(id: string, cache: SafeCacheStore): void {
  const payload = cache[id];
  if (payload) {
    console.log(payload.identifier.toLowerCase()); // Безопасно
  }
}
```

*   **Ошибка 2: Попытка использовать сложные объекты в качестве ключей**
    *   *Проблема:* Попытка сконструировать тип вида `Record<TargetPayload, string>` завершится ошибкой компиляции: `Type 'TargetPayload' does not satisfy the constraint 'keyof any'`. JavaScript не поддерживает использование сложных ссылочных объектов в качестве ключей обычных POJO-объектов (они неявно кастятся к строке `"[object Object]"`).
    *   *Решение:* Если по логике приложения ключом должен быть сложный объект, используйте встроенную структуру данных `Map<K, V>` в сочетании с обобщениями.

```typescript
// ПЛОХО (Объекты нельзя использовать как ключи в Record)
// type InvalidRecord = Record<TargetPayload, string>; // ! Ошибка компиляции

// ХОРОШО (Использование встроенного класса Map со строгой типизацией)
export const objectStoreMap = new Map<TargetPayload, string>();
```

*   **Ошибка 3: Нарушение контроля полноты из-за принудительного приведения типов (`as`)**
    *   *Проблема:* Разработчик обходит компилятор, объявляя неполный словарь и кастя его к строгому типу: `const map = { pending: {...} } as Record<DataState, StatusConfig>`. Сборка проекта проходит успешно, но в рантайме при обращении к отсутствующему статусу `map["fulfilled"]` возникнет ошибка.
    *   *Решение:* Никогда не используйте приведение типов `as` для обхода контроля полноты. Если вам действительно нужен частично заполненный справочник, используйте комбинацию утилит `Partial<Record<K, T>>`.
