# Декларативный вывод ошибок валидации в шаблоне

## БЫСТРЫЙ СТАРТ

*   **Декларативный вывод ошибок** — это подход к визуализации состояния валидности формы в HTML-шаблоне с использованием встроенного управляющего синтаксиса (`@if`, `@else`) и реактивных флагов состояния контрола.
*   **Состояния элементов управления (Control States):**
    *   `touched` / `untouched` — взаимодействовал ли пользователь с полем (был ли установлен и убран фокус).
    *   `dirty` / `pristine` — изменял ли пользователь значение внутри поля (вводил ли символы).
    *   `invalid` / `valid` / `pending` — текущий статус валидности.
*   **Используйте:** Для вывода точечных, понятных человеку предупреждений о неверном вводе строго в тот момент, когда пользователь завершил работу с полем, предотвращая появление "красного" интерфейса при первой загрузке страницы.
*   **Не используйте:** Тяжелые функции-парсеры ошибок непосредственно внутри интерполяционных выражений шаблона `{{ getErrorMessage() }}` — это приводит к сотням паразитных вызовов на каждом микрособытии детекции изменений.

### Шаблон 1: Базовый условный вывод ошибок с Control Flow
*   **Назначение:** Описание компонента контактных данных `ContactDetails` со стандартными проверками на обязательность и формат почты, выводящими ошибки только после взаимодействия пользователя с полем.

#### 1. Файл логики: `contact-details.ts`
```typescript
import { Component, ChangeDetectionStrategy, inject } from '@angular/core';
import { NonNullableFormBuilder, ReactiveFormsModule, Validators } from '@angular/forms';

@Component({
  selector: 'app-contact-details',
  // standalone: true опускается по умолчанию начиная с v19
  imports: [ReactiveFormsModule], // Импортируем только модуль реактивных форм
  templateUrl: './contact-details.html',
  styleUrl: './contact-details.css',
  changeDetection: ChangeDetectionStrategy.OnPush // OnPush гарантирует стабильный FPS
})
export class ContactDetails { // Имя класса не содержит устаревшего суффикса Component
  private readonly fb = inject(NonNullableFormBuilder);

  // Описываем плоскую форму
  public readonly contactForm = this.fb.group({
    email: ['', [Validators.required, Validators.email]]
  });

  public submit(): void {
    if (this.contactForm.invalid) {
      return;
    }
    console.log('Данные верны:', this.contactForm.getRawValue());
  }
}
```

#### 2. Файл разметки: `contact-details.html`
```html
<form [formGroup]="contactForm" (ngSubmit)="submit()" class="contact-form">
  <div class="field-container">
    <label for="email">Электронная почта:</label>
    
    <!-- 
      Связываем инпут с контролом. 
      Применяем условные CSS-классы валидности для подсветки границ инпута.
    -->
    <input 
      id="email" 
      type="email" 
      formControlName="email" 
      class="theme-input"
      [class.input-invalid]="contactForm.controls.email.invalid && contactForm.controls.email.touched"
    />

    <!-- 
      Выводим контейнер ошибок только при выполнении двух условий:
      1. Контрол имеет ошибки (.errors !== null).
      2. Пользователь убрал фокус с поля (.touched === true).
    -->
    @if (contactForm.controls.email.touched && contactForm.controls.email.errors; as errors) {
      <div class="error-wrapper">
        @if (errors['required']) {
          <span class="error-msg">Электронная почта обязательна для заполнения</span>
        }
        @if (errors['email']) {
          <span class="error-msg">Пожалуйста, введите валидный адрес почты</span>
        }
      </div>
    }
  </div>

  <button type="submit" [disabled]="contactForm.invalid" class="action-btn">Сохранить</button>
</form>
```

### Шаблон 2: Универсальный переиспользуемый компонент вывода ошибок
*   **Назначение:** Создание изолированного дочернего компонента `FieldError`, который принимает экземпляр `AbstractControl` в качестве сигнального `input` и декларативно рендерит переведенные тексты ошибок, исключая дублирование верстки во всем приложении.

#### 1. Файл логики: `field-error.ts`
```typescript
import { Component, ChangeDetectionStrategy, input, computed } from '@angular/core';
import { AbstractControl } from '@angular/forms';

@Component({
  selector: 'app-field-error',
  imports: [],
  templateUrl: './field-error.html',
  styleUrl: './field-error.css',
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class FieldError {
  // Принимаем обязательный входной сигнал с контролом формы
  public readonly control = input.required<AbstractControl>();

  // Декларативно вычисляем текст ошибки на основе сигнального графа зависимостей
  public readonly errorMessage = computed<string | null>(() => {
    const ctrl = this.control();
    
    // Показываем ошибку только после взаимодействия с полем
    if (!ctrl.invalid || !ctrl.touched) {
      return null;
    }

    const errors = ctrl.errors;
    if (!errors) {
      return null;
    }

    // Сопоставляем технические ключи ошибок с понятными человеку текстами
    if (errors['required']) {
      return 'Поле обязательно для заполнения';
    }
    if (errors['email']) {
      return 'Некорректный формат электронной почты';
    }
    if (errors['minlength']) {
      const requiredLength = errors['minlength'].requiredLength;
      return `Минимальная длина значения: ${requiredLength} символов`;
    }
    if (errors['pattern']) {
      return 'Значение не соответствует требуемому формату';
    }

    // Если встретилась неизвестная ошибка, возвращаем общий системный ключ
    return 'Некорректное значение поля';
  });
}
```

#### 2. Файл разметки: `field-error.html`
```html
<!-- Рендерим сообщение, если computed-сигнал вернул строку ошибки -->
@if (errorMessage(); as msg) {
  <span class="error-label">{{ msg }}</span>
}
```

#### 3. Файл стилей: `field-error.css`
```css

  color: var(--error-text);
  font-size: 0.78rem;
  font-weight: 500;
  display: inline-block;
  margin-top: 4px;
}
```

### Шаблон 3: Кросс-полевой вывод ошибок всей группы (Form-level errors)
*   **Назначение:** Описание компонента выбора периода дат `DateRangeSelector` с кастомной кросс-валидацией группы, выводящей общее предупреждение "Дата начала не может быть позже даты окончания".

#### 1. Файл логики: `date-range-selector.ts`
```typescript
import { Component, ChangeDetectionStrategy, inject } from '@angular/core';
import { NonNullableFormBuilder, ReactiveFormsModule, AbstractControl, ValidationErrors, ValidatorFn } from '@angular/forms';

/**
 * Кросс-полевой валидатор группы.
 * Проверяет логическую связь между двумя контролами
 */
export const dateRangeValidator: ValidatorFn = (control: AbstractControl): ValidationErrors | null => {
  const start = control.get('startDate')?.value;
  const end = control.get('endDate')?.value;

  if (!start || !end) {
    return null; // Если даты не выбраны, пропускаем проверку (это задача required)
  }

  const startTime = new Date(start).getTime();
  const endTime = new Date(end).getTime();

  // Если дата старта больше даты окончания — возвращаем ошибку на уровень всей группы FormGroup
  return startTime > endTime ? { dateRangeInvalid: true } : null;
};

@Component({
  selector: 'app-date-range-selector',
  imports: [ReactiveFormsModule],
  templateUrl: './date-range-selector.html',
  styleUrl: './date-range-selector.css',
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class DateRangeSelector {
  private readonly fb = inject(NonNullableFormBuilder);

  public readonly dateForm = this.fb.group({
    startDate: ['', [Validators.required]],
    endDate: ['', [Validators.required]]
  }, {
    // Подключаем кросс-валидатор в конфигурационный объект на уровне группы
    validators: [dateRangeValidator]
  });

  public submitPeriod(): void {
    if (this.dateForm.invalid) {
      return;
    }
    console.log('Период валиден:', this.dateForm.getRawValue());
  }
}
```

#### 2. Файл разметки: `date-range-selector.html`

```html
      <label for="end">Дата окончания:</label>

</form>
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Архитектура состояний взаимодействия (Touched vs Dirty)
Одной из распространенных ошибок при проектировании интерфейсов является поспешный вывод ошибок валидации. Если выводить ошибки сразу при появлении пустого поля, пользователь увидит "красную" форму с сообщениями "Поле обязательно" в ту же секунду, как открыл страницу. Это создает негативный пользовательский опыт (UX).

Для предотвращения этого в Angular заложена сложная машина состояний взаимодействия:
*   **`touched` / `untouched`:** Контрол переходит в статус `touched` строго тогда, когда пользователь установил фокус в инпут, а затем убрал его (произошло нативное событие `blur`). Это идеальный триггер для вывода ошибок обязательности заполнения (`Validators.required`). Пользователь зашел в поле, ничего не ввел, ушел дальше — выводим ошибку.
*   **`dirty` / `pristine`:** Контрол переходит в статус `dirty` в момент, когда пользователь физически изменил значение внутри поля (ввел хотя бы один символ). Это идеальный триггер для вывода ошибок формата (например, `Validators.pattern` или `Validators.email`). Пока пользователь не начал вводить текст, сообщать ему о неверном формате бессмысленно.

Правильное комбинирование этих флагов (например, `control.touched && control.invalid`) гарантирует, что ошибки появятся на экране своевременно и ненавязчиво.

### 2. Производительность рендеринга шаблонов и вред геттеров
Рассмотрим частый антипаттерн вывода ошибок в шаблоне:
```html
<!-- АНТИПАТТЕРН: Вызов метода в шаблоне -->
<span>{{ getEmailErrorMessage() }}</span>
```
```typescript
public getEmailErrorMessage(): string {
  const ctrl = this.form.controls.email;
  if (ctrl.hasError('required')) return 'Обязательно';
  return '';
}
```
Почему этот код работает медленно?
В силу архитектуры Angular, интерполяционные выражения в HTML-шаблоне вычисляются при **каждом** проходе цикла детекции изменений (Change Detection). Если пользователь скроллит страницу, двигает мышкой или в фоновом режиме работает веб-сокет, метод `getEmailErrorMessage()` будет вызываться сотни раз в секунду. Это приводит к лишней нагрузке на процессор (CPU) и деградации производительности (просадкам FPS).

Использование сигнального реактивного контейнера (такого как `FieldError` в Шаблоне 2 с computed-сигналом) полностью решает эту проблему. Поскольку `computed` мемоизирует результат вычисления, формула отработает строго один раз при реальном изменении статуса контрола, а при всех последующих холостых циклах детекции изменений Angular мгновенно вернет готовую строку ошибки из кэша памяти.

### 3. Детальный пошаговый разбор вычисления ошибок
Проследим шаги перерасчета в компоненте `FieldError` (Шаблон 2) при вводе некорректного email:

1.  **Ввод данных:** Пользователь начинает вводить `"mario@"` в поле email. Контрол переходит в состояние `dirty`. Статус валидности — `INVALID` (так как почта не окончена).
2.  **Действие:** Пользователь убирает фокус с поля. Контрол переходит в состояние `touched`.
3.  **Оповещение:** Смена флага `touched` помечает связанный `FieldError` как dirty.
4.  **Срабатывание computed:** Запускается формула `errorMessage`.
5.  **Анализ условий:**
    *   Проверяется `!ctrl.invalid || !ctrl.touched` (Ложно, так как контрол невалиден и уже тронут).
    *   Считывается объект ошибок `errors` (содержит `{ email: true }`).
    *   Срабатывает проверка `if (errors['email'])`.
    *   Метод возвращает строку `'Некорректный формат электронной почты'`.
6.  **Рендеринг:** Значение кэшируется. В HTML-шаблоне блок `@if` рендерит спан с текстом ошибки на экране.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Преждевременное отображение ошибок при инициализации формы**
    *   *Симптомы:* Пользователь заходит на страницу создания профиля и мгновенно видит красные рамки вокруг пустых полей и сообщения об ошибках.
    *   *Причина:* Пропуск проверок состояний взаимодействия (`touched` или `dirty`) в условных конструкциях шаблона: `@if (control.errors) { ... }`.
    *   *Решение:* Всегда добавляйте условие `.touched` или `.dirty` перед анализом объекта ошибок контрола.

```html
<!-- ПЛОХО (Ошибка отобразится сразу при загрузке страницы на пустом поле) -->
@if (form.controls.email.errors) { <span>Ошибка</span> }

<!-- ХОРОШО (Ошибка появится только после того, как пользователь покинул поле) -->
@if (form.controls.email.touched && form.controls.email.errors) { <span>Ошибка</span> }
```

*   **Ошибка 2: Использование `form.value` вместо `form.getRawValue()` при отправке данных**
    *   *Симптомы:* Данные из отключенных (disabled) полей формы не отправляются на сервер, хотя пользователь видит их заполненными на экране.
    *   *Физика процесса:* Метод `form.value` по спецификации Angular полностью исключает свойства отключенных контролов из результирующего объекта.
    *   *Решение:* Для полной отправки всей структуры данных (включая заблокированные поля) всегда вызывайте метод `form.getRawValue()`.

```typescript
// ПЛОХО (Исключит значения всех отключенных полей из отправки)
sendData(): void {
  const payload = this.form.value; 
}

// ХОРОШО (Вернет полную структуру формы независимо от флагов блокировки контролов)
sendDataCorrectly(): void {
  const payload = this.form.getRawValue();
}
```

*   **Ошибка 3: Ошибки очистки при условном скрытии полей через `@if`**
    *   *Симптомы:* Поле скрывается в шаблоне при выключении чекбокса, но форма продолжает оставаться невалидной, и кнопка отправки заблокирована.
    *   *Причина:* Скрытие HTML-элементов через `@if` удаляет их из DOM, но не влияет на состояние реактивной модели формы в TypeScript. Контрол продолжает существовать в памяти со своими валидаторами.
    *   *Решение:* При скрытии полей всегда принудительно отключайте их через `.disable()` (что автоматически выключит их валидаторы) или полностью удаляйте контрол из группы с помощью `.removeControl()`.
