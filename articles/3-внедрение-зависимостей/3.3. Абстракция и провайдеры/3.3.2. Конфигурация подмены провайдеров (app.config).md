# 3.3.2. Конфигурация подмены провайдеров (app.config)

## БЫСТРЫЙ СТАРТ

*   **Файл `app.config.ts`** — это центральная точка глобальной конфигурации современного Standalone-приложения Angular. Он содержит объект типа `ApplicationConfig`, в массиве `providers` которого регистрируются все глобальные системные и пользовательские зависимости.
*   **Механики подмены зависимостей (DI Providers):**
    *   `useClass` — указывает Angular создать экземпляр конкретного класса при запросе токена.
    *   `useValue` — связывает токен со статическим значением (конфигурацией, замороженным объектом, строкой).
    *   `useFactory` — запускает функцию-фабрику для динамического вычисления зависимости в рантайме. Внутри современных фабрик можно напрямую использовать `inject()`, что избавляет от написания массива `deps`.
    *   `useExisting` — создает псевдоним (alias), перенаправляя запрос с одного токена на другой, уже зарегистрированный.
*   **Используйте их для:** переключения приложения между реальным HTTP-сервисом и Mock-заглушкой на основе флагов окружения, динамического конфигурирования библиотек, инжекции настроек сред (Environment Config).
*   **Не используйте их:** для локальных сервисов уровня экранов или форм. Такие зависимости должны объявляться в массиве `providers` соответствующих компонентов.

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Динамическая подмена класса на основе флага окружения (`useClass`)
*   **Назначение:** Настройка `app.config.ts` для переключения между реальным HTTP-провайдером данных и Mock-заглушкой для локальной разработки.

```typescript
import { ApplicationConfig, provideZoneChangeDetection } from '@angular/core';
import { provideRouter } from '@angular/router';
import { routes } from './app.routes';
import { DATA_SERVICE_TOKEN } from './data-service.token';
import { HttpDataService } from './http-data.service';
import { MockDataService } from './mock-data.service';

// Симулируем флаг окружения (в реальном проекте импортируется из environments/environment)
const environment = {
  production: false
};

export const appConfig: ApplicationConfig = {
  providers: [
    // Настраиваем оптимизацию зон
    provideZoneChangeDetection({ eventCoalescing: true }),
    // Регистрируем глобальные маршруты
    provideRouter(routes),
    
    // Настраиваем динамическую подмену реализации для интерфейса-токена
    {
      provide: DATA_SERVICE_TOKEN,
      // Если production равен true — Angular создаст HttpDataService, иначе — легкий MockDataService
      useClass: environment.production ? HttpDataService : MockDataService
    }
  ]
};
```

### Шаблон 2: Динамический фабричный провайдер с использованием функционального `inject()` (`useFactory`)
*   **Назначение:** Создание и конфигурация службы, требующей для инициализации другие глобальные зависимости, без использования устаревшего и ненадежного массива `deps`.

```typescript
import { ApplicationConfig, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { AUTH_TOKEN } from './auth.token';
import { SecureApiClient } from './secure-api-client.service';

export const appConfig: ApplicationConfig = {
  providers: [
    {
      provide: SecureApiClient,
      // Описываем функцию-фабрику для создания экземпляра класса
      useFactory: () => {
        // Извлекаем необходимые зависимости прямо внутри фабрики с помощью inject().
        // Нам больше не нужно писать громоздкое "deps: [HttpClient, AUTH_TOKEN]"
        const http = inject(HttpClient);
        const auth = inject(AUTH_TOKEN);
        
        const baseEndpoint = 'https://api.secure-gateway.com/v1';
        return new SecureApiClient(http, auth, baseEndpoint);
      }
    }
  ]
};
```

### Шаблон 3: Предоставление статических настроек окружения через `useValue`
*   **Назначение:** Безопасное внедрение неизменяемой глобальной конфигурации в приложение.

```typescript
import { ApplicationConfig, InjectionToken } from '@angular/core';

export interface AppConfigSettings {
  apiEndpoint: string;
  enableDebugLogs: boolean;
}

export const APP_SETTINGS_TOKEN = new InjectionToken<AppConfigSettings>('APP_SETTINGS_TOKEN');

// Замораживаем объект конфигурации для предотвращения его изменения в рантайме
const productionSettings: AppConfigSettings = Object.freeze({
  apiEndpoint: 'https://api.production.company.com/v2',
  enableDebugLogs: false
});

export const appConfig: ApplicationConfig = {
  providers: [
    {
      provide: APP_SETTINGS_TOKEN,
      // Внедряем готовый неизменяемый объект конфигурации в DI-контейнер
      useValue: productionSettings
    }
  ]
};
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Анатомия глобального объекта `ApplicationConfig` и Environment Injector
В архитектуре Angular, начиная с эпохи Standalone-компонентов, функция `bootstrapApplication(AppComponent, appConfig)` инициализирует корневое окружение. Массив `providers` внутри `appConfig` напрямую формирует конфигурацию **Root Environment Injector**. 

Этот инжектор является глобальным пространством имен для всех зависимостей, которые должны быть доступны во всем приложении (включая лениво загружаемые маршруты). Когда компилятор Angular встречает синтаксис `{ provide, use... }` в `appConfig`, он регистрирует рецепт создания зависимости в глобальной хэш-таблице инжектора.

### 2. Преимущества функционального `useFactory` без использования массива `deps`
В классическом Angular (до версии 14) при описании `useFactory` разработчик был обязан синхронно вести две структуры: саму функцию-фабрику и массив зависимостей `deps`:
```typescript
// УСТАРЕВШИЙ ПОДХОД
{
  provide: MyService,
  useFactory: (http: HttpClient) => new MyService(http),
  deps: [HttpClient] // Легко допустить опечатку или перепутать порядок аргументов
}
```
Любая ошибка в порядке перечисления токенов в `deps` приводила к тому, что в аргументы фабрики передавались неверные экземпляры служб, вызывая трудноотлавливаемые ошибки типизации в рантайме.

Современный Angular позволяет вызывать `inject()` непосредственно в теле функции `useFactory`. В момент выполнения фабрики Angular временно устанавливает её контекст активным. Это позволяет писать чистый, самодокументируемый код инициализации, где зависимости запрашиваются декларативно прямо по месту использования, полностью исключая необходимость в поддержке массива `deps`.

### 3. Детальный пошаговый разбор динамической подмены класса (`useClass`)
Разберем алгоритм работы DI-контейнера при инициализации `appConfig`:
1.  **Регистрация рецепта:** При запуске приложения инжектор считывает провайдер:
    ```typescript
    { provide: DATA_SERVICE_TOKEN, useClass: MockDataService }
    ```
    В системный реестр записывается: «При запросе `DATA_SERVICE_TOKEN` запустить конструктор класса `MockDataService`».
2.  **Запрос зависимости:** Компонент вызывает `inject(DATA_SERVICE_TOKEN)`.
3.  **Анализ провайдера:** Инжектор видит, что для токена зарегистрировано свойство `useClass: MockDataService`.
4.  **Разрешение зависимостей класса:** Инжектор анализирует зависимости самого класса `MockDataService`. Если классу требуются другие службы, они также извлекаются из DI-контейнера.
5.  **Создание и кэширование:** Инжектор вызывает оператор `new MockDataService(...)`, сохраняет созданный экземпляр в кэше синглтонов и возвращает ссылку компоненту.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Ошибка циклической зависимости при некорректном связывании через `useExisting`**
    *   *Проблема:* Разработчик пытается создать псевдоним для сервиса, но по ошибке указывает в `useExisting` тот же самый токен: `{ provide: Logger, useExisting: Logger }`. Это вызывает бесконечную рекурсию при попытке разрешения зависимости и падение приложения.
    *   *Решение:* `useExisting` должен всегда ссылаться на **другой**, уже зарегистрированный и осязаемый в DI-контейнере токен.

```typescript
// ПЛОХО (Токен ссылается сам на себя, вызывая бесконечную петлю поиска)
// { provide: AppLogger, useExisting: AppLogger }

// ХОРОШО (Перенаправляем запрос с абстрактного AppLogger на конкретный ConsoleLogger)
{ provide: AppLogger, useExisting: ConsoleLogger }
```

*   **Ошибка 2: Нарушение иммутабельности и утечки реактивности при использовании `useValue`**
    *   *Проблема:* Разработчик внедряет объект конфигурации через `useValue` и пытается динамически изменять его свойства из разных компонентов: `settings.apiEndpoint = 'new_val'`. Обычные объекты передаются по ссылке, из-за чего неконтролируемое изменение глобального конфига ломает предсказуемость состояния приложения и Change Detection.
    *   *Решение:* Всегда замораживайте объекты, передаваемые в `useValue`, с помощью `Object.freeze()`. Если конфигурация должна меняться в процессе работы, внедряйте полноценный сервис с Сигналами или RxJS-потоками вместо сырого объекта настроек.

*   **Ошибка 3: Избыточное дублирование конфигураций сред в коде сервисов**
    *   *Проблема:* Разработчик хардкодит URL-адреса и ключи API непосредственно внутри кода классов `HttpDataService`. Это делает невозможным развертывание одного и того же бандла в разных тестовых контурах (dev, staging, prod) без полной пересборки всего приложения.
    *   *Решение:* Вынесите все динамические параметры среды в токен `APP_SETTINGS_TOKEN`. Передавайте конкретные значения полей в файле `app.config.ts`, считывая их из переменных окружения. Классы сервисов должны оставаться чистыми исполнителями, принимающими настройки строго из DI-контейнера.
