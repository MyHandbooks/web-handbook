# 3.1.1. Создание глобального синглтона (providedIn root)

## БЫСТРЫЙ СТАРТ

*   **Глобальный синглтон (Singleton Service)** — это служба, которая существует в единственном экземпляре на все работающее приложение и предоставляет единый источник правды для разделяемых данных или бизнес-логики.
*   **Конфигурация `providedIn: 'root'`** — современный декларативный способ регистрации службы в глобальном корневом инжекторе Angular (Root Injector). Это делает класс доступным для внедрения в любой точке приложения.
*   **Tree-shakability (Вытряхивание мертвого кода):** Сервисы, зарегистрированные через `providedIn: 'root'`, автоматически поддерживают tree-shaking. Если служба объявлена, но не внедрена ни в один компонент или другой сервис, сборщик проекта (Webpack, Esbuild) полностью удалит её код из финального бандла.
*   **Используйте его для:** глобального состояния (профиль авторизованного пользователя, настройки темы, языковые пакеты), кешей запросов, общих сетевых API-клиентов и служб логирования.
*   **Не используйте его:** для хранения состояния, которое должно уничтожаться вместе с уходом пользователя с конкретного экрана или закрытием UI-компонента (например, черновик заполняемой формы).

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Глобальная синглтон-служба состояния конфигурации
*   **Назначение:** Описание глобальной службы для хранения и синхронного изменения настроек интерфейса на базе Сигналов.

```typescript
import { Injectable, signal, computed } from '@angular/core';

export interface AppConfig {
  theme: 'light' | 'dark';
  sidebarOpen: boolean;
}

// Декоратор Injectable с параметром providedIn: 'root' регистрирует службу как глобальный синглтон
@Injectable({
  providedIn: 'root'
})
export class AppConfigService {
  // Инициализируем реактивное состояние через приватный изменяемый сигнал
  private readonly configState = signal<AppConfig>({
    theme: 'dark',
    sidebarOpen: true
  });

  // Экспортируем сигналы чтения для предотвращения несанкционированного изменения состояния извне
  readonly currentTheme = computed(() => this.configState().theme);
  readonly isSidebarOpen = computed(() => this.configState().sidebarOpen);

  // Публичный метод для изменения темы
  public toggleTheme(): void {
    this.configState.update((current) => ({
      ...current,
      theme: current.theme === 'light' ? 'dark' : 'light'
    }));
  }

  // Публичный метод для переключения видимости сайдбара
  public toggleSidebar(): void {
    this.configState.update((current) => ({
      ...current,
      sidebarOpen: !current.sidebarOpen
    }));
  }
}
```

### Шаблон 2: Внедрение и использование в Standalone-компоненте
*   **Назначение:** Безопасное подключение синглтон-сервиса в автономный компонент с помощью функционального API `inject()`.

```typescript
import { Component, inject } from '@angular/core';
import { AppConfigService } from './app-config.service';

@Component({
  selector: 'app-shell-header',
  // Указываем standalone-режим, исключая необходимость в NgModule
  standalone: true,
  template: `
    <header class="app-header">
      <!-- Вызываем сигналы для декларативного обновления интерфейса -->
      <button (click)="configService.toggleSidebar()">Toggle Menu</button>
      <span>Текущая тема: {{ configService.currentTheme() }}</span>
      <button (click)="configService.toggleTheme()">Переключить тему</button>
    </header>
  `,
  styles: [`
    .app-header { display: flex; gap: 16px; padding: 12px; }
  `]
})
export class ShellHeaderComponent {
  // Внедряем глобальную службу через современную функцию inject()
  // Конструктор компонента остается полностью пустым и чистым
  protected readonly configService = inject(AppConfigService);
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Физика дерева инжекторов (Injector Tree) и корневой инжектор
Система внедрения зависимостей в Angular построена по иерархическому принципу. Существует две основные ветви инжекторов:
*   **Environment Injector Hierarchy:** Корневое окружение приложения. На самом верху находится `NullInjector`, затем `VoidInjector`, далее `PlatformInjector` и, наконец, **Root Injector** (где хранятся провайдеры уровня приложения, объявленные через `providedIn: 'root'`).
*   **Node Injector Hierarchy (Element Injectors):** Дерево инжекторов, которое строится на базе иерархии DOM-элементов и компонентов. Каждый компонент или директива может создавать собственный локальный инжектор.

Когда компонент запрашивает зависимость через `inject(AppConfigService)`, Angular сначала ищет службу в локальном Node Injector компонента. Если служба там не зарегистрирована, поиск поднимается вверх по дереву родительских компонентов вплоть до Root Injector. Служба с `providedIn: 'root'` всегда обнаруживается в корневом инжекторе и возвращается в виде одного и того же экземпляра (синглтона) для любого просителя.

### 2. Как работает Tree-shaking (вытряхивание мертвого кода) для Injectable
В старых версиях Angular (до Angular 6) сервисы регистрировались в массиве `providers: [MyService]` внутри `@NgModule`. При таком подходе класс сервиса жестко связывался с модулем. Сборщик проекта (Webpack, Rollup, Esbuild) не мог определить, используется ли этот сервис реально, и всегда включал его код в итоговый бандл.

Декларация `@Injectable({ providedIn: 'root' })` разворачивает зависимость. Теперь не модуль или приложение импортирует сервис, а сам сервис указывает, где он должен быть зарегистрирован. Во время компиляции, если сборщик анализирует граф зависимостей приложения и видит, что на класс `AppConfigService` нет ни одного вызова `inject()` или упоминания в конструкторах, код класса полностью удаляется из сборки. Это значительно уменьшает размер приложения при росте кодовой базы.

### 3. Детальный пошаговый разбор жизненного цикла глобального синглтона
1.  **Компиляция:** Angular компилирует декоратор `@Injectable({ providedIn: 'root' })`, генерируя статический метод фабрики внутри класса сервиса.
2.  **Запуск приложения (Bootstrap):** Приложение инициализируется в файле `main.ts` через `bootstrapApplication()`. Создается инжектор Root Injector. На этом этапе экземпляр класса `AppConfigService` **еще не создан** (ленивая инициализация).
3.  **Первый вызов (On-Demand Instantiation):** Пользователь переходит на страницу, где рендерится `ShellHeaderComponent`. Компонент запрашивает зависимость `inject(AppConfigService)`.
4.  **Создание экземпляра:** Root Injector проверяет свой внутренний реестр экземпляров (Map). Не найдя там созданного объекта, он запускает сгенерированную фабрику, создает экземпляр `AppConfigService`, сохраняет ссылку в реестре и возвращает её компоненту.
5.  **Последующие вызовы:** Любой другой компонент на других страницах при вызове `inject(AppConfigService)` мгновенно получает ту же самую ссылку из Map-реестра Root Injector.
6.  **Уничтожение:** Экземпляр сервиса живет в памяти до полного закрытия или перезагрузки вкладки приложения в браузере.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Случайное дублирование экземпляра синглтона**
    *   *Проблема:* Разработчик объявил глобальный сервис с `providedIn: 'root'`, но также добавил его в массив `providers: [AppConfigService]` конкретного компонента. В итоге этот компонент и его дочерние элементы получают локальную копию сервиса, которая уничтожается вместе с компонентом, нарушая принцип единого источника правды.
    *   *Решение:* Никогда не дублируйте глобальные сервисы в локальных массивах `providers` компонентов. Если сервис должен быть глобальным, он регистрируется только через `providedIn: 'root'`.

```typescript
// ПЛОХО (Спецификация providers перезапишет синглтон для этой ветви компонентов)
@Component({
  selector: 'app-profile-feature',
  standalone: true,
  providers: [AppConfigService], // ! Ошибка: Создает локальный дубликат глобального сервиса
  template: `...`
})
export class ProfileFeatureComponent {}
```

*   **Ошибка 2: Циклическая зависимость (Circular Dependency)**
    *   *Проблема:* Сервис `AuthService` внедряет через `inject` службу `ApiService`, а служба `ApiService` внедряет обратно `AuthService`. При инициализации Angular не может разрешить, какой класс создавать первым, и выбрасывает ошибку: `Circular dependency in DI detected`.
    *   *Решение:* Избегайте циклического связывания. Вынесите общую логику (например, хранение токена) в третий независимый сервис `TokenStoreService`, который будет внедряться в обе службы без создания цикла.

*   **Ошибка 3: Утечка глобального состояния при переходах между экранами**
    *   *Проблема:* Синглтон-сервис накапливает данные (например, результаты поиска) при работе пользователя на конкретном экране. Когда пользователь уходит на другую страницу и возвращается, на экране отображаются старые "загрязненные" данные, так как синглтон никогда самостоятельно не уничтожается и хранит состояние в оперативной памяти.
    *   *Решение:* Если данные специфичны для конкретного экрана, используйте локальные сервисы (Scoped Services) уровня компонента. Если сервис обязан быть синглтоном, реализуйте в нем явный метод сброса состояния `reset()` и вызывайте его при уничтожении UI-компонента через хук жизненного цикла `onDestroy` или modern `DestroyRef`.

```typescript
import { Injectable, signal, DestroyRef, inject } from '@angular/core';

@Component({
  selector: 'app-search-screen',
  standalone: true,
  template: `...`
})
export class SearchScreenComponent {
  private readonly searchService = inject(SearchService);
  
  constructor() {
    // Безопасно очищаем глобальный кэш при уходе пользователя с экрана поиска
    inject(DestroyRef).onDestroy(() => {
      this.searchService.clearResults();
    });
  }
}
```
