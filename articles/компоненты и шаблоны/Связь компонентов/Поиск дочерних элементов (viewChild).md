# Поиск дочерних элементов (viewChild)

## БЫСТРЫЙ СТАРТ

*   **Сигнальные запросы (viewChild)** — это современный реактивный интерфейс для поиска и получения ссылок на дочерние элементы, директивы или компоненты внутри HTML-шаблона родителя. Он полностью заменяет устаревший декоратор `@ViewChild()`.
*   **Реактивность вместо хуков:** В отличие от старого подхода, требующего написания императивного кода в хуке `ngAfterViewInit`, `viewChild()` возвращает стандартный Сигнал чтения. Это позволяет декларативно связывать дочерние элементы с вычислениями `computed()` или побочными эффектами `effect()`.
*   **Правила использования:**
    *   **Используйте:** Для управления фокусом элементов, программного вызова публичных методов дочерних компонентов, интеграции сторонних JS-библиотек, требующих прямой работы с DOM, или динамического рендеринга шаблонов.
    *   **Не используйте:** Прямой доступ к внутренностям дочерних компонентов нарушает принцип инкапсуляции. Вместо вызова внутренних методов ребенка для изменения его состояния старайтесь использовать стандартные реактивные каналы связи — входные свойства `input()` и события `output()`.

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Строго типизированный поиск компонента через `viewChild.required`
*   **Назначение:** Получение гарантированной ссылки на экземпляр дочернего компонента для программного вызова его публичного метода `executeAction()`.

```typescript
import { Component, ChangeDetectionStrategy, viewChild } from '@angular/core';

@Component({
  selector: 'app-child-worker',
  standalone: true,
  template: `<div class="worker">Инструмент готов к работе.</div>`,
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class ChildWorkerComponent {
  // Публичный метод, который родитель планирует вызвать программно
  executeAction(param: string): void {
    console.log(`Дочерний воркер выполнил задачу: ${param}`);
  }
}

@Component({
  selector: 'app-parent-controller',
  standalone: true,
  imports: [ChildWorkerComponent],
  template: `
    <div class="panel">
      <!-- Размещение дочернего компонента в шаблоне родителя -->
      <app-child-worker />
      <button (click)="triggerChildAction()">Запустить задачу ребенка</button>
    </div>
  `,
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class ParentControllerComponent {
  // Определение обязательного запроса дочернего компонента по его классу.
  // Использование .required гарантирует, что тип сигнала будет ChildWorkerComponent без undefined.
  readonly workerComponent = viewChild.required(ChildWorkerComponent);

  triggerChildAction(): void {
    // Безопасный вызов метода дочернего компонента. 
    // TypeScript уверен, что свойство не равно undefined, благодаря required-запросу.
    this.workerComponent().executeAction('ЗАПУСК_СИСТЕМЫ');
  }
}
```

### Шаблон 2: Поиск нативного HTML-элемента с опцией чтения (read) и эффектом
*   **Назначение:** Получение ссылки на нативный HTML-элемент `ElementRef` с помощью строкового селектора шаблона для управления фокусом инпута внутри реактивного эффекта.

```typescript
import { Component, ChangeDetectionStrategy, viewChild, ElementRef, effect } from '@angular/core';

@Component({
  selector: 'app-focus-controller',
  standalone: true,
  imports: [],
  template: `
    <div class="form-group">
      <!-- Локальная переменная шаблона #textInput указывает на нативный элемент -->
      <input #textInput type="text" placeholder="Введите имя..." class="theme-input">
      <button (click)="focusOnInput()">Установить фокус вручную</button>
    </div>
  `,
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class FocusControllerComponent {
  // Поиск элемента по его строковому маркеру '#textInput'.
  // Опция { read: ElementRef } сообщает Angular о необходимости вернуть обертку ElementRef,
  // предоставляющую прямой доступ к нативному DOM-узлу.
  readonly inputEl = viewChild.required<ElementRef<HTMLInputElement>>('textInput', {
    read: ElementRef
  });

  constructor() {
    // Реактивный эффект отслеживает изменения и готов работать с элементом
    effect(() => {
      const elementRef = this.inputEl();
      // Выполняем логгирование или базовые настройки при доступности узла в DOM
      if (elementRef) {
        console.log('Нативный HTML-элемент успешно привязан к сигнальному графу:', elementRef.nativeElement);
      }
    });
  }

  focusOnInput(): void {
    // Безопасное обращение к нативному API браузера для установки фокуса
    this.inputEl().nativeElement.focus();
  }
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Архитектурная эволюция: Сигналы против декораторов
В классических версиях Angular декоратор `@ViewChild('el') el!: ElementRef;` обладал существенными недостатками:
1.  **Отсутствие реактивности:** Свойство класса было обычной переменной. Если элемент динамически монтировался или удалялся из DOM (например, под управлением `*ngIf`), родительский класс не мог узнать об этом событии автоматически.
2.  **Жесткая привязка к хукам:** Единственным безопасным местом для чтения ссылок на DOM был хук жизненного цикла `ngAfterViewInit`. Это приводило к накоплению императивного кода разметки в одном месте и мешало проектировать изолированные реактивные конвейеры.

Новое Сигнальное API полностью решает эти проблемы. Метод `viewChild()` возвращает реактивный узел `Signal`:
*   Сигнал обновляется автоматически. Как только Angular монтирует элемент в DOM, значение сигнала меняется. Если элемент удаляется, сигнал принимает значение `undefined`.
*   Поскольку это стандартный Сигнал, вы можете использовать его внутри `computed()` для динамического вычисления состояний или внутри `effect()` для реагирования на появление элементов. Потребность в хуке `ngAfterViewInit` в большинстве случаев полностью отпадает.

### 2. Строгий контроль типов: `viewChild` против `viewChild.required`
По умолчанию функция `viewChild` возвращает сигнал с типом `Signal<T | undefined>`. Наличие `undefined` в типе является защитой компилятора. Если элемент скрыт внутри условного блока `@if`, Angular не сможет найти его при первичной отрисовке. Использование безопасной навигации (`this.myEl()?.nativeElement`) предотвращает падение приложения.

Однако часто структура шаблона является статической, и элемент присутствует на экране всегда. Для таких случаев спроектирован метод `viewChild.required`. Он гарантирует компилятору, что элемент будет найден, и исключает `undefined` из возвращаемого типа. Если Angular по какой-то причине не сможет обнаружить элемент во время инициализации шаблона, он мгновенно выбросит понятную ошибку в консоль браузера, не маскируя баг в коде.

### 3. Пошаговый разбор выполнения поиска и обновления ссылки
В процессе рендеринга `FocusControllerComponent` выполняются следующие шаги:
1.  **Создание пустого реактивного узла:** При инициализации класса компонента `viewChild` регистрирует пустой сигнал со значением `undefined`.
2.  **Первичный проход шаблона (Рендеринг):** Ivy строит DOM-дерево и находит тег `input` с маркером `#textInput`.
3.  **Анализ метаданных запросов:** По завершении фазы отрисовки шаблона Angular считывает маркер, оборачивает его в `ElementRef` (согласно инструкции `read`) и записывает значение в созданный ранее сигнал.
4.  **Запуск эффектов:** Запись значения переводит зависимые реактивные узлы в статус `dirty`. Срабатывает зарегистрированный в конструкторе `effect()`, получая доступ к актуальному нативному DOM-элементу.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Попытка чтения значения `viewChild` на этапе ранней инициализации (например, в `ngOnInit`)**
    *   *Симптомы:* Метод `viewChild()` возвращает `undefined`, а вызов обязательного `viewChild.required()` приводит к падению приложения с ошибкой: `RuntimeError: NG0100: ExpressionChangedAfterItHasBeenCheckedError...` или крашу в консоли при попытке прочитать элемент слишком рано.
    *   *Физика процесса:* Метод `ngOnInit` вызывается до того, как Angular скомпилировал и построил HTML-шаблон текущего компонента. В этот момент DOM-дерево еще физически не существует в памяти, и любые поисковые запросы вернут пустоту.
    *   *Решение:* Читать сигналы запросов внутри реактивных эффектов `effect()`, хука `ngAfterViewInit`, либо в ответ на интерактивные действия пользователя (клики, ввод).

```typescript
// ОШИБКА: Попытка прочитать DOM-элемент до его отрисовки
ngOnInit(): void {
  // Элемент еще не создан! Произойдет runtime crash в случае required
  const el = this.inputEl().nativeElement; 
}

// ИСПРАВЛЕНИЕ: Чтение внутри безопасной реактивной зоны эффекта
constructor() {
  effect(() => {
    // Эффект гарантированно сработает только тогда, когда сигнал получит значение
    const nativeEl = this.inputEl().nativeElement;
    console.log('Элемент готов к работе:', nativeEl);
  });
}
```

*   **Ошибка 2: Пропуск параметра `read` при поиске нативного DOM-элемента у тега компонента**
    *   *Симптомы:* Сигнал возвращает экземпляр класса Angular-компонента вместо ожидаемого нативного HTML-элемента, что делает невозможным обращение к свойствам типа `style`, `focus()` или `classList`.
    *   *Физика процесса:* Если применить селектор `#element` к тегу Angular-компонента (например, `<app-child #child />`), по умолчанию поисковый движок Angular возвращает ссылку на экземпляр класса этого компонента. Чтобы получить доступ к физической DOM-коробке этого компонента, необходимо явно попросить Angular вернуть `ElementRef`.
    *   *Решение:* Передавать конфигурационный объект `{ read: ElementRef }` в качестве второго аргумента функции запроса.

```typescript
// ОШИБКА: Запрос вернет экземпляр класса ChildComponent, а не HTML-узел
readonly childComponent = viewChild('child');

// ИСПРАВЛЕНИЕ: Явное указание на необходимость извлечь ElementRef
readonly childDomNode = viewChild('child', { read: ElementRef });
```

*   **Ошибка 3: Потеря ссылок и утечки при динамическом переключении Control Flow**
    *   *Симптомы:* При скрытии элемента через `@if` сигнал успешно принимает значение `undefined`, но в связанных фоновых JS-обработчиках (например, слушателях событий сторонних библиотек на нативном DOM) остаются висеть «мертвые» ссылки на удаленный элемент, что приводит к утечкам памяти.
    *   *Физика процесса:* `@if` полностью удаляет узел из DOM. Если сторонняя библиотека была привязана к этому узлу, браузер не сможет удалить его из памяти, так как на него все еще ссылается JS-код библиотеки.
    *   *Решение:* Написать очищающий эффект, который отслеживает значение сигнала и своевременно деактивирует внешние обработчики при возвращении сигнала в `undefined`.

```typescript
constructor() {
  // ИСПРАВЛЕНИЕ: Очищающий эффект для интеграции с внешними JS-библиотеками
  effect((onCleanup) => {
    const elementRef = this.inputEl();

    if (elementRef) {
      // Инициализируем сторонний плагин на найденном элементе
      const pluginInstance = new ThirdPartyPlugin(elementRef.nativeElement);

      // onCleanup вызывается автоматически перед следующим запуском эффекта или при уничтожении
      onCleanup(() => {
        // Уничтожаем плагин и освобождаем ссылки на DOM
        pluginInstance.destroy();
      });
    }
  });
}
```
