# Обработка сетевых ошибок и авто-повтор (Retry)

## БЫСТРЫЙ СТАРТ

*   **Класс `HttpErrorResponse`** — специализированный объект Angular, инкапсулирующий всю системную информацию о сетевом сбое. Он разделяет ошибки на два типа: клиентские/сетевые (сбой DNS, отсутствие интернета, обрыв соединения) и серверные (статусы HTTP-ответов 4xx и 5xx).
*   **Авто-повтор запросов (Retry):** Стратегия автоматического повторного выполнения запроса к API при кратковременных сбоях сети с целью минимизации отказов UI без участия пользователя.
*   **Правила использования:**
    *   **Используйте авто-повтор:** Только для идемпотентных HTTP-методов (преимущественно GET-запросы, реже PUT и DELETE), которые при многократном вызове не изменяют состояние базы данных и не создают дублирующих транзакций.
    *   **Не используйте авто-повтор:** Для неидемпотентных методов (POST-запросы, например, создание заказа или проведение платежа) во избежание дублирования сущностей. Также отключайте повторы при авторизационных ошибках (401 Unauthorized, 403 Forbidden) или некорректных данных клиента (400 Bad Request, 404 Not Found) — эти ошибки требуют изменения состояния сессии или ввода пользователя, и повторный запрос к серверу без изменений гарантированно завершится сбоем.

### Шаблон 1: HTTP GET-запрос с экспоненциальной задержкой (Exponential Backoff)
*   **Назначение:** Реализация надежного сетевого метода, который при временных сетевых сбоях автоматически повторяет запрос до 3 раз, увеличивая паузу между попытками и исключая повтор для заведомо ошибочных статусов (400, 401, 404).

```typescript
import { Injectable, inject } from '@angular/core';
import { HttpClient, HttpErrorResponse } from '@angular/common/http';
import { Observable, timer, throwError } from 'rxjs';
import { retry, catchError } from 'rxjs/operators';

export interface TargetDataPayload {
  id: string;
  payloadContent: string;
}

@Injectable({
  providedIn: 'root'
})
export class ResilientDataService {
  // Внедряем HttpClient через функциональный inject()
  private readonly http = inject(HttpClient);
  
  // URL-адрес защищенного или нестабильного API
  private readonly endpoint = 'https://api.unstable-cloud-service.com/v1/data';

  /**
   * Безопасно запрашивает данные с автоматическим повтором при сбоях
   */
  public fetchResilientData(): Observable<TargetDataPayload> {
    return this.http.get<TargetDataPayload>(this.endpoint).pipe(
      // Используем современную перегрузку оператора retry() с объектом конфигурации (RxJS v7.4+)
      retry({
        // Максимальное количество попыток повторной отправки запроса
        count: 3,
        // Описываем функцию-фабрику для вычисления задержки перед каждым повтором
        delay: (error: HttpErrorResponse, retryCount: number): Observable<number> => {
          // Если ошибка вызвана действиями клиента — не перегружаем сеть и сразу прокидываем её дальше
          if (error.status === 400 || error.status === 401 || error.status === 403 || error.status === 404) {
            // Возбуждаем ошибку внутри коллбэка delay. Это прерывает конвейер повторов и завершает поток
            throw error; 
          }

          // Рассчитываем экспоненциальную задержку: 1-й раз — 1сек, 2-й раз — 2сек, 3-й раз — 4сек
          const calculatedDelay = Math.pow(2, retryCount - 1) * 1000;
          
          // Добавляем небольшой случайный фактор (Jitter) до 200мс, чтобы распределить нагрузку от клиентов на сервер
          const jitter = Math.random() * 200;
          const finalDelay = calculatedDelay + jitter;

          console.warn(`[Retry] Попытка №${retryCount} завершилась сбоем. Следующий запрос через ${Math.round(finalDelay)}мс.`);
          
          // Возвращаем холодный поток таймера. Когда таймер сработает, retry осуществит повторную подписку на HTTP-запрос
          return timer(finalDelay);
        }
      }),
      // Локально перехватываем ошибку, если все попытки авто-повтора были исчерпаны
      catchError((error: HttpErrorResponse): Observable<never> => {
        console.error('[Error] Все попытки повтора запроса исчерпаны. Ошибка:', error.message);
        
        // Преобразуем техническую ошибку в стандартизированное сообщение для бизнес-логики UI
        const readableErrorMessage = this.extractHumanReadableMessage(error);
        
        // Передаем типизированную ошибку дальше в нижестоящие подписки
        return throwError(() => new Error(readableErrorMessage));
      })
    );
  }

  /**
   * Парсит HttpErrorResponse и формирует понятное человеку сообщение
   */
  private extractHumanReadableMessage(error: HttpErrorResponse): string {
    if (error.status === 0) {
      return 'Не удалось установить соединение с сервером. Проверьте ваше подключение к интернету.';
    }
    if (error.status >= 500) {
      return 'На сервере произошла непредвиденная ошибка. Мы уже работаем над её устранением.';
    }
    return `Сервер вернул ошибку: ${error.error?.message || error.statusText || 'Неизвестный сбой'}`;
  }
}
```

### Шаблон 2: Функциональный перехватчик для глобального логирования и маппинга ошибок
*   **Назначение:** Глобальный обработчик (Interceptor) всех HTTP-запросов приложения, который централизованно отслеживает сбои связи, передает логи в систему мониторинга (например, Sentry) и форматирует системные ошибки.

```typescript
import { HttpInterceptorFn, HttpErrorResponse } from '@angular/common/http';
import { throwError } from 'rxjs';
import { catchError } from 'rxjs/operators';

// Описываем стандартную структуру ошибки валидации, которую может возвращать бэкенд
export interface BackendValidationError {
  errorCode: string;
  message: string;
  fields?: Record<string, string[]>;
}

export const GlobalErrorInterceptor: HttpInterceptorFn = (req, next) => {
  // Пропускаем запрос дальше по цепочке выполнения
  return next(req).pipe(
    catchError((error: unknown) => {
      // Убеждаемся, что перехваченная ошибка является объектом HttpErrorResponse
      if (error instanceof HttpErrorResponse) {
        // Логируем критические ошибки в консоль или отправляем во внешнюю систему мониторинга
        if (error.status === 0 || error.status >= 500) {
          console.error(`[Global Monitor] Сетевая или Серверная ошибка на эндпоинте: ${req.url}`, error);
        }

        // Пытаемся извлечь валидационные ошибки из JSON-ответа сервера
        const backendError = error.error as BackendValidationError | null;
        
        if (backendError && backendError.errorCode) {
          // Если бэкенд вернул структурированное API-исключение
          return throwError(() => ({
            status: error.status,
            code: backendError.errorCode,
            message: backendError.message,
            validationFields: backendError.fields || null,
            originalError: error
          }));
        }
      }

      // Если это неструктурированная ошибка, просто пробрасываем её без изменений
      return throwError(() => error);
    })
  );
};
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Физика сетевых сбоев и реактивные потоки в RxJS
Когда вы делаете HTTP-вызов в Angular, `HttpClient` возвращает так называемый «холодный конечный Observable поток» (Cold Finite Observable). В штатном режиме этот поток испускает ровно один элемент (объект ответа) и завершается сигналом `complete`. 

Однако, если происходит сетевой сбой (таймаут, обрыв сокета) или сервер возвращает статус $\ge 400$, конвейер RxJS генерирует событие `error`. Согласно фундаментальной спецификации реактивного программирования (The Observable Contract), событие `error` является терминальным сигналом. Это означает, что **после возникновения ошибки поток мгновенно уничтожается в памяти, закрывается и больше никогда не сможет испустить ни одного значения**.

Оператор `retry` обходит это ограничение физики потоков. Он перехватывает сигнал `error` до того, как тот успеет дойти до конечного подписчика (коллбэка `.subscribe({ error })`), уничтожает упавшую подписку и **автоматически осуществляет повторную подписку (re-subscribe)** на исходный холодный Observable-источник. Это заставляет Angular заново запустить весь жизненный цикл генерации XHR-запроса в браузере.

### 2. Экспоненциальная задержка и феномен Thundering Herd (Лавина запросов)
В простейших реализациях разработчики настраивают немедленный повторный запрос при сбое: `retry(3)`. В условиях промышленного enterprise-приложения это деструктивная практика. 

Если сервер бэкенда или база данных перегружены и начали отвечать ошибками `503 Service Unavailable`, мгновенная отправка повторных запросов от тысяч активных клиентов приведет к лавинообразному увеличению трафика (явление Thundering Herd). Это окончательно перегрузит сетевые шлюзы и не позволит серверу восстановиться в штатный режим.

Применение **Exponential Backoff** решает эту проблему путем пропорционального увеличения интервала ожидания перед каждой последующей попыткой:
$$\text{Delay} = 2^{\text{attempt} - 1} \times \text{BaseInterval}$$

Для исключения ситуации, когда тысячи распределенных клиентов одновременно отправляют повторные запросы по синхронным таймерам (например, ровно через 2000мс), в формулу добавляется случайная погрешность — **Jitter (шум)**. Jitter искусственно размывает время старта запросов по шкале времени, создавая плавную сетевую нагрузку на инфраструктуру.

### 3. Пошаговый разбор выполнения авто-повтора
Давайте проследим жизненный цикл вызова `fetchResilientData()` из Шаблона 1 при возникновении кратковременной ошибки DNS (сетевой статус `0`):

1.  **Попытка 1:** Запрос уходит на сервер. Сетевой кабель отключен $\rightarrow$ браузер возвращает сбой $\rightarrow$ `HttpClient` выбрасывает `HttpErrorResponse` со статусом `0`.
2.  **Запуск механизма `retry`:**
    *   Оператор `retry` ловит ошибку. Счётчик попыток `retryCount` равен `1`.
    *   Срабатывает функция `delay()`. Проверяется статус: `error.status` равен `0` (не входит в список исключений `400, 401, 403, 404`). Повтор разрешен.
    *   Вычисляется задержка: $2^{1-1} \times 1000\text{мс} = 1000\text{мс} + \text{jitter} \approx 1120\text{мс}$.
    *   Возвращается `timer(1120)`. Поток засыпает на 1.12 секунды.
3.  **Попытка 2:** По истечении таймера `retry` повторно подписывается на сетевой поток. Происходит вторая отправка запроса. Сеть восстановилась $\rightarrow$ сервер возвращает успешный ответ `200 OK`.
4.  **Результат:** Данные без препятствий проходят через оператор `retry` и попадают в метод `.subscribe({ next })` UI-компонента. Компонент даже не узнал, что на сетевом уровне произошел кратковременный сбой.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Повтор неидемпотентных POST-запросов (The Duplicate Transaction Bug)**
    *   *Симптомы:* Пользователи жалуются на двойное списание средств при оплате или на создание дубликатов сущностей при медленном интернете.
    *   *Физика процесса:* Клиент отправляет POST-запрос на создание платежа. Сервер успешно принял запрос, обработал его, списал деньги, но в момент отправки HTTP-ответа `200 OK` произошел обрыв связи. Клиент получил статус `0` (таймаут) и запустил авто-повтор. Второй POST-запрос ушел на сервер и выполнил транзакцию повторно.
    *   *Решение:* Никогда не настраивайте авто-повтор для методов, изменяющих состояние данных на сервере, без использования механизма уникальных ключей идемпотентности (`Idempotency-Key` в заголовках) на бэкенде.

```typescript
// ОШИБКА: Авто-повтор на POST-запросе создания сущности без контроля идемпотентности
// return this.http.post(url, body).pipe(retry(3));

// ХОРОШО: Авто-повтор применяется строго на безопасном GET-запросе чтения
return this.http.get(url).pipe(retry({ count: 3, delay: 1000 }));
```

*   **Ошибка 2: Бесконечный цикл повторов при отсутствии лимита (Endless Retry Memory Leak)**
    *   *Симптомы:* Вкладка браузера зависает или сильно нагружает процессор устройства после длительного нахождения на странице при выключенном сервере API.
    *   *Физика процесса:* Разработчик не указал свойство `count` в конфигурации `retry`, рассчитывая на бесконечный автоматический коннект. При постоянном отсутствии сети поток начинает бесконечно генерировать таймеры и повторные XHR-соединения, забивая очередь макрозадач (MacroTask Queue) событийного цикла браузера (Event Loop).
    *   *Решение:* Всегда устанавливайте жесткое максимальное ограничение на количество попыток повтора (`count`) и обязательно используйте авто-отписку при уходе пользователя со страницы.

```typescript
// ОШИБКА: Потенциально бесконечный цикл повторов без ограничений
// return this.http.get(url).pipe(retry({ delay: 1000 }));

// ХОРОШО: Установлен лимит попыток и времени жизни подписки
return this.http.get(url).pipe(
  retry({ count: 3, delay: 2000 }),
  takeUntilDestroyed(this.destroyRef) // Гарантирует отписку при уничтожении компонента
);
```

*   **Ошибка 3: Преждевременное скрытие ошибки в перехватчике (Silent Fallback Bug)**
    *   *Симптомы:* Запрос падает с сетевой ошибкой, но UI-компонент думает, что запрос прошел успешно, и отображает пустой интерфейс вместо сообщения об ошибке.
    *   *Физика процесса:* Разработчик обрабатывает ошибку в глобальном интерцепторе и возвращает дефолтное значение через оператор `of` (например, `catchError(() => of([]))`). Так как `of` возвращает успешный элемент в поток, нижестоящие компоненты получают пустой массив и не догадываются о произошедшем сетевом сбое.
    *   *Решение:* Перехватчики должны выполнять только задачи логирования, обновления токенов или глобального мониторинга, а затем обязательно пробрасывать ошибку дальше через `throwError(() => error)`, чтобы конечный компонент мог корректно отобразить состояние ошибки в интерфейсе.
