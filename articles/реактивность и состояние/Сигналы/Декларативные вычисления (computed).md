# Декларативные вычисления (computed)

## БЫСТРЫЙ СТАРТ

*   **Вычисляемый сигнал (`Signal<T>`)** — реактивный примитив чтения в Angular, предназначенный для декларативного расчета производного (зависимого) состояния на основе одного или нескольких других сигналов.
*   **Два фундаментальных свойства:**
    *   **Ленивые вычисления (Lazy Evaluation):** Формула расчета внутри `computed` не запускается в момент изменения сигналов-источников. Вычисление происходит только тогда, когда кто-то физически пытается прочитать значение вычисляемого сигнала (например, шаблон при рендеринге).
    *   **Мемоизация (Memoization):** Результат вычисления кэшируется в памяти. Если сигналы-источники изменились, но итоговый результат вычисления остался прежним (или источники не менялись вовсе), Angular мгновенно вернет сохраненное значение из кэша без повторного выполнения функции расчета.
*   **Правила использования:**
    *   **Используйте:** Для фильтрации списков, суммирования цен в корзине, форматирования дат, комбинирования данных профиля или подсчета количества выбранных элементов.
    *   **Не используйте:** Для выполнения побочных эффектов (Side Effects) — внутри `computed` категорически запрещено изменять другие сигналы, отправлять HTTP-запросы или манипулировать DOM напрямую. Вычисляемый поток должен оставаться чистой функцией (Pure Function).

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Базовое форматирование и объединение сигналов
*   **Назначение:** Синтез строки полного имени пользователя на основе сигналов имени, фамилии и роли с автоматическим кэшированием результата.

```typescript
import { Component, computed, signal } from '@angular/core';

@Component({
  selector: 'app-user-badge',
  standalone: true,
  template: `
    <div class="badge">
      <!-- При чтении fullName() Angular вернет значение из кэша, если имя или фамилия не менялись -->
      <h4>Пользователь: {{ fullName() }}</h4>
      <button (click)="changeName()">Сменить имя</button>
    </div>
  `
})
export class UserBadgeComponent {
  // Инициализируем исходные изменяемые сигналы
  public readonly firstName = signal<string>('Иван');
  public readonly lastName = signal<string>('Иванов');
  public readonly userRole = signal<string>('архитектор');

  // Декларативно вычисляем новое состояние на основе трех сигналов.
  // Сигнал fullName автоматически становится доступен только для чтения (тип Signal, а не WritableSignal).
  public readonly fullName = computed<string>(() => {
    const rawRole = this.userRole().toUpperCase();
    return `${this.lastName()} ${this.firstName()} [${rawRole}]`;
  });

  /**
   * Изменяет имя пользователя
   */
  public changeName(): void {
    this.firstName.set('Алексей');
  }
}
```

### Шаблон 2: Производительная фильтрация списка по поисковой строке
*   **Назначение:** Динамический отбор элементов массива на основе поискового запроса. Использование `computed` предотвращает повторную фильтрацию при каждом цикле Change Detection, если фильтры не менялись.

```typescript
import { Component, computed, signal } from '@angular/core';

export interface CatalogProduct {
  id: string;
  title: string;
}

@Component({
  selector: 'app-product-catalog',
  standalone: true,
  template: `
    <div class="catalog">
      <!-- Связываем ввод текста с изменением сигнала searchQuery -->
      <input 
        type="text" 
        placeholder="Поиск по каталогу..." 
        (input)="updateSearch($event)" 
      />

      <ul>
        <!-- Рендерим отфильтрованный список продуктов -->
        @for (product of filteredProducts(); track product.id) {
          <li>{{ product.title }}</li>
        } @empty {
          <li>Ничего не найдено</li>
        }
      </ul>
    </div>
  `
})
export class ProductCatalogComponent {
  // Сигнал, хранящий поисковый запрос пользователя
  public readonly searchQuery = signal<string>('');

  // Сигнал, хранящий полный сырой список товаров из базы данных
  public readonly allProducts = signal<CatalogProduct[]>([
    { id: '1', title: 'Angular Architecture Guide' },
    { id: '2', title: 'TypeScript Deep Dive' },
    { id: '3', title: 'RxJS Masterclass' }
  ]);

  // Вычисляем отфильтрованный список.
  // Сигнал автоматически реагирует на изменения searchQuery() или allProducts().
  public readonly filteredProducts = computed<CatalogProduct[]>(() => {
    const query = this.searchQuery().toLowerCase().trim();
    const products = this.allProducts();

    if (!query) {
      return products; // Если строка поиска пуста, возвращаем исходный список
    }

    // Возвращаем отфильтрованный массив. Метод filter создает новую ссылку.
    return products.filter((product) =>
      product.title.toLowerCase().includes(query)
    );
  });

  /**
   * Обновляет поисковый сигнал при вводе текста
   */
  public updateSearch(event: Event): void {
    const inputElement = event.target as HTMLInputElement;
    this.searchQuery.set(inputElement.value);
  }
}
```

### Шаблон 3: Динамическое отслеживание зависимостей (Ветвление логики)
*   **Назначение:** Описание вычислений со сложной условной логикой, где Angular динамически регистрирует или отписывается от сигналов в зависимости от текущей ветки выполнения.

```typescript
import { Component, computed, signal } from '@angular/core';

@Component({
  selector: 'app-conditional-tracker',
  standalone: true,
  template: `
    <div class="tracker">
      <p>Отображаемое значение: {{ processedValue() }}</p>

      <button (click)="toggleMode()">Переключить режим ({{ useAlternative() ? 'Альтернативный' : 'Стандартный' }})</button>
      <button (click)="updateSourceA()">Изменить Источник А</button>
      <button (click)="updateSourceB()">Изменить Источник Б</button>
    </div>
  `
})
export class ConditionalTrackerComponent {
  // Флаг переключения логической ветки вычислений
  public readonly useAlternative = signal<boolean>(false);
  
  // Два независимых источника данных
  public readonly sourceA = signal<number>(10);
  public readonly sourceB = signal<number>(500);

  // Декларативно рассчитываем значение с условным ветвлением
  public readonly processedValue = computed<string>(() => {
    // Если флаг равен false — Angular считывает и регистрирует зависимость только от sourceA().
    // Изменения сигнала sourceB в этот момент будут полностью игнорироваться,
    // и вычисление processedValue запускаться не будет!
    if (!this.useAlternative()) {
      return `[Стандарт] Результат: ${this.sourceA() * 2}`;
    }

    // Если флаг переключается в true — Angular мгновенно исключает sourceA из зависимостей
    // и начинает реагировать исключительно на изменения sourceB().
    return `[Альтернатива] Результат: ${this.sourceB() + 100}`;
  });

  public toggleMode(): void {
    this.useAlternative.update((val) => !val);
  }

  public updateSourceA(): void {
    this.sourceA.update((n) => n + 1);
  }

  public updateSourceB(): void {
    this.sourceB.update((n) => n + 1);
  }
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Концепция Glitch-Free (Отсутствие мерцания состояния) и ориентированный граф
В классических реактивных библиотеках (например, старых версиях MobX или сложных цепочках RxJS) существует проблема «глитчей» (Glitches / Diamond Dependency Problem). Представьте граф зависимостей, напоминающий ромб:

```
    [Сигнал А]
     /      \
[Сигнал Б]  [Сигнал В]
     \      /
   [Вычисление Г]
```

Если Сигнал А изменяется, он одновременно инициирует обновление Сигнала Б и Сигнала В. Если система реактивности работает на модели мгновенного проталкивания (Push), Вычисление Г может запуститься дважды: сначала когда обновится Сигнал Б (но в Сигнал В еще будет находиться старое значение), а затем когда обновится Сигнал В. Это приводит к кратковременному несоответствию (глитчу) данных на экране и паразитной нагрузке на процессор.

Angular Signals гарантируют **Glitch-Free** выполнение. Благодаря Push-Pull модели, при изменении Сигнала А вычисляемый сигнал Г не пересчитывается мгновенно. Он лишь получает уведомление о том, что его зависимости стали «грязными». И только во время фазы стягивания (Pull) Angular строит топологический порядок обхода графа и вычисляет итоговое значение Г ровно один раз, когда все его предки (Б и В) гарантированно приняли свои окончательные стабильные состояния.

### 2. Физика мемоизации: Как работает версионирование сигналов
Для обеспечения высокой производительности Angular не выполняет глубокое сравнение возвращаемых объектов внутри `computed`. Вместо этого фреймворк использует внутренний механизм **версионирования (Version Tracking)**.

Каждый реактивный узел (Producer) имеет внутренний целочисленный счетчик версии — `version`. При каждом изменении значения (вызовах `set` или `update`) версия инкрементируется: `version++`.

Вычисляемый сигнал (Consumer) при первом запуске запоминает версии всех сигналов, которые он считал во время выполнения формулы. При последующем запросе значения `computed` Angular сначала опрашивает зависимости: «Каковы ваши текущие версии?». Если версии всех сигналов-источников совпадают с сохраненными версиями предыдущего расчета, Angular полностью пропускает выполнение формулы вычисления и мгновенно возвращает закэшированное значение.

### 3. Пошаговый разбор динамического отслеживания (Branch Pruning)
Давайте детально разберем, как Angular динамически перестраивает граф зависимостей в Шаблоне 3 (Динамическое отслеживание):

1.  **Первый запуск:** Шаблон рендерит `processedValue()`. Функция `computed` запускается.
2.  **Анализ ветки:** Считывается сигнал `useAlternative()`, значение которого равно `false`.
3.  **Регистрация зависимости:** Код заходит в блок `if`. Считывается сигнал `sourceA()`.
4.  **Сборка графа:** Angular фиксирует: «Для расчета `processedValue` сейчас нужны `useAlternative` и `sourceA`». Сигнал `sourceB` не считывался, поэтому связь с ним не создается.
5.  **Изменение sourceB:** Пользователь нажимает «Изменить Источник Б». Сигнал `sourceB` увеличивает версию, но так как связи с `processedValue` нет, никакого уведомления по графу не отправляется. Лишних расчетов не происходит.
6.  **Переключение режима:** Пользователь нажимает «Переключить режим». Сигнал `useAlternative` меняет значение на `true` и помечает `processedValue` как dirty.
7.  **Пересчет:** При чтении `processedValue` формула запускается заново. Теперь код заходит в альтернативную ветку: считывается `useAlternative()` и `sourceB()`.
8.  **Перестройка графа (Pruning):** Angular видит, что `sourceA` больше не участвовал в расчете. Он полностью удаляет связь с `sourceA` и регистрирует новую связь с `sourceB`. Теперь вычисления будут реагировать только на изменения флага и Источника Б.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Попытка изменения состояния (Side Effects) внутри computed**
    *   *Симптомы:* Ошибка рантайма `Computed member cannot modify reactive state` или бесконечный цикл зависания страницы.
    *   *Физика процесса:* Разработчик пытается обновить другой сигнал внутри формулы вычисления: `computed(() => { this.anotherSignal.set(1); })`. Изменение реактивного состояния внутри вычислений нарушает стабильность графа зависимостей, так как приводит к непредсказуемой лавине dirty-уведомлений в момент, когда граф пытается стабилизироваться. Angular жестко блокирует любые попытки записи в сигналы внутри контекста `computed`.
    *   *Решение:* Перенесите логику побочных эффектов в обработчики событий (клики, ввод) или, в крайних случаях, используйте `effect()`.

```typescript
// ОШИБКА: Запись в сигнал внутри computed строго запрещена
// const total = computed(() => {
//   this.logSignal.set('computed started'); 
//   return this.count() * 2;
// });

// ИСПРАВЛЕНИЕ:computed должен оставаться чистой функцией
const total = computed(() => this.count() * 2);
```

*   **Ошибка 2: Попытка выполнения асинхронных операций (HTTP, setTimeout)**
    *   *Симптомы:* Вычисляемый сигнал не реагирует на изменение зависимостей, возвращает `undefined` или некорректные данные.
    *   *Физика процесса:* Разработчик пытается запустить асинхронный процесс внутри computed: `computed(() => { setTimeout(() => this.count(), 1000) })`. Реактивный контекст Angular отслеживает зависимости **строго синхронно**. Как только функция `computed` завершает свое физическое выполнение, Angular закрывает регистрацию связей. Сигнал `count()`, вызванный асинхронно через секунду, будет считан вне реактивного контекста, и связь с ним создана не будет.
    *   *Решение:* Для асинхронных операций, таких как сетевые запросы, используйте RxJS-потоки (через `toObservable`) или современный `resource` API (Angular 19+).

```typescript
// ОШИБКА: Синхронный контекст не зарегистрирует count() как зависимость
// const asyncValue = computed(() => {
//   let res;
//   setTimeout(() => { res = this.count() * 2; }, 1000);
//   return res;
// });

// ИСПРАВЛЕНИЕ: Вычисления должны быть строго синхронными
const syncValue = computed(() => this.count() * 2);
```

*   **Ошибка 3: Опора на нереактивные переменные**
    *   *Симптомы:* Обычная переменная класса изменилась, но вычисляемый сигнал не запустил перерасчет и отображает старое значение.
    *   *Физика процесса:* Разработчик использует внутри `computed` обычную переменную класса: `computed(() => this.count() * this.multiplier)`. Обычные переменные не умеют отправлять dirty-уведомления по графу зависимостей. Angular пересчитает `computed` только тогда, когда обновится сигнал `count()`. Если изменится только `multiplier`, вычисляемый сигнал продолжит выдавать старое закэшированное значение из памяти.
    *   *Решение:* Все переменные, изменение которых должно приводить к пересчету интерфейса, должны быть объявлены как сигналы.

```typescript
// ОШИБКА: Изменение multiplier не запустит пересчет computed автоматически
// multiplier = 2;
// total = computed(() => this.count() * this.multiplier);

// ИСПРАВЛЕНИЕ: Все участники вычислений обернуты в сигналы
public readonly multiplier = signal<number>(2);
public readonly total = computed(() => this.count() * this.multiplier());
```
