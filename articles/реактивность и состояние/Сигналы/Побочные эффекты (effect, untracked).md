# Побочные эффекты (effect, untracked)

## БЫСТРЫЙ СТАРТ

*   **Функция побочного эффекта `effect()`** — реактивный примитив Angular, который запускает переданный в него коллбэк каждый раз, когда изменяются сигналы, считанные внутри этого коллбэка. Эффект всегда запускается асинхронно в фазе планировщика микрозадач (Microtask Scheduler) после завершения отрисовки интерфейса.
*   **Функция `untracked(fn)`** — служебная обертка, позволяющая считать значение любого сигнала внутри реактивного контекста (`computed`, `effect`), **не регистрируя его как зависимость**. Изменение сигнала внутри `untracked` не приведет к перезапуску эффекта или пересчету вычислений.
*   **Правила использования:**
    *   **Используйте `effect()`:** Для синхронизации сигнального состояния со сторонними нереактивными API (сохранение данных в `localStorage`, отрисовка графиков на `Canvas`, инициализация плагинов вроде `Chart.js`), ручного логирования или отправки событий аналитики.
    *   **Не используйте `effect()`:** Для синхронизации или перезаписи других сигналов (запись в сигналы внутри эффектов заблокирована по умолчанию во избежание бесконечных циклов). Для этого строго используйте `computed` или `linkedSignal`.

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Синхронизация состояния с LocalStorage (Базовый эффект)
*   **Назначение:** Автоматическое и надежное сохранение настроек интерфейса (например, текущей цветовой темы) в локальное хранилище браузера при каждом изменении сигнала.

```typescript
import { Component, effect, signal } from '@angular/core';

@Component({
  selector: 'app-theme-selector',
  standalone: true,
  template: `
    <div class="theme-card">
      <p>Активная тема: {{ currentTheme() }}</p>
      <button (click)="setTheme('light-theme')">Светлая</button>
      <button (click)="setTheme('dark-theme')">Темная</button>
    </div>
  `
})
export class ThemeSelectorComponent {
  // Инициализируем сигнал, пытаясь сначала прочитать сохраненное значение из хранилища
  public readonly currentTheme = signal<string>(
    localStorage.getItem('app_user_theme') || 'dark-theme'
  );

  constructor() {
    // Объявляем эффект внутри конструктора (активный контекст внедрения зависимостей).
    // Эффект автоматически отслеживает считывание сигнала currentTheme().
    effect(() => {
      const themeValue = this.currentTheme();
      
      // Синхронизируем состояние с нереактивным API LocalStorage
      localStorage.setItem('app_user_theme', themeValue);
      
      // Манипулируем классами нативного DOM элемента body
      document.body.className = themeValue;
      
      console.log(`[Effect Log] Тема успешно обновлена в LocalStorage и DOM на: ${themeValue}`);
    });
  }

  public setTheme(themeName: string): void {
    this.currentTheme.set(themeName);
  }
}
```

### Шаблон 2: Эффект очистки ресурсов через onCleanup
*   **Назначение:** Использование встроенного в эффект коллбэка очистки для уничтожения фоновых асинхронных таймеров, подписок или сокет-соединений перед каждым повторным запуском эффекта или при уничтожении компонента.

```typescript
import { Component, effect, signal } from '@angular/core';

@Component({
  selector: 'app-polling-monitor',
  standalone: true,
  template: `
    <div class="monitor">
      <p>Текущий интервал опроса сервера: {{ pollingIntervalMs() }}мс</p>
      <button (click)="setInterval(1000)">Быстро (1с)</button>
      <button (click)="setInterval(5000)">Медленно (5с)</button>
    </div>
  `
})
export class PollingMonitorComponent {
  // Сигнал, управляющий временем задержки опроса сервера
  public readonly pollingIntervalMs = signal<number>(3000);

  constructor() {
    // Внедряем эффект. Коллбэк эффекта принимает функцию регистрации очистки onCleanup.
    effect((onCleanup) => {
      const interval = this.pollingIntervalMs();
      
      console.log(`[Effect] Запускаем опрос сервера с интервалом в ${interval}мс...`);
      
      // Инициализируем нативный асинхронный таймер
      const timerId = setInterval(() => {
        this.fetchDiagnosticData();
      }, interval);

      // Регистрируем функцию очистки. Angular гарантированно выполнит её:
      // 1. Непосредственно ПЕРЕД следующим повторным запуском этой формулы эффекта.
      // 2. В момент полного уничтожения компонента (Destroy).
      onCleanup(() => {
        console.warn(`[Effect Cleanup] Очищаем предыдущий таймер ID: ${timerId}`);
        clearInterval(timerId); // Защита от утечки памяти и наложения параллельных таймеров
      });
    });
  }

  private fetchDiagnosticData(): void {
    console.log('[Network] Диагностический запрос отправлен на сервер...');
  }

  public setInterval(ms: number): void {
    this.pollingIntervalMs.set(ms);
  }
}
```

### Шаблон 3: Чтение нереактивных данных через untracked()
*   **Назначение:** Запуск эффекта в ответ на изменение одного сигнала-триггера с параллельным считыванием вспомогательных данных из другого сигнала, изменения которого НЕ должны вызывать повторный запуск эффекта.

```typescript
import { Component, effect, signal, untracked } from '@angular/core';

@Component({
  selector: 'app-analytics-tracker',
  standalone: true,
  template: `
    <div class="tracker">
      <p>Счетчик событий: {{ clickCount() }}</p>
      <p>Имя активного профиля: {{ activeProfileName() }}</p>

      <button (click)="registerClick()">Зафиксировать клик (Отправить лог)</button>
      <button (click)="changeProfileName()">Обновить имя профиля</button>
    </div>
  `
})
export class AnalyticsTrackerComponent {
  // Сигнал-триггер. Каждое его изменение должно запускать эффект.
  public readonly clickCount = signal<number>(0);
  
  // Вспомогательный сигнал контекста
  public readonly activeProfileName = signal<string>('Архитектор Фронтенда');

  constructor() {
    effect(() => {
      // Считываем сигнал напрямую. Он регистрируется как активная зависимость эффекта.
      const clicks = this.clickCount();

      // Оборачиваем чтение сигнала в untracked().
      // Мы получаем актуальное строковое значение сигнала, но Angular НЕ создает связь в графе.
      // Изменение имени профиля теперь не будет запускать этот эффект заново!
      const profile = untracked(() => this.activeProfileName());

      this.sendAnalyticsPayload(clicks, profile);
    });
  }

  private sendAnalyticsPayload(clicksCount: number, userName: string): void {
    if (clicksCount === 0) return;
    console.log(`[Analytics] Клик №${clicksCount} отправлен. Профиль отправителя: ${userName}`);
  }

  public registerClick(): void {
    this.clickCount.update((count) => count + 1);
  }

  public changeProfileName(): void {
    // Это изменение НЕ вызовет отправку лога аналитики, так как сигнал прочитан через untracked()
    this.activeProfileName.set('Ведущий Инженер');
  }
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Планировщик микрозадач (Microtask Scheduler) и жизненный цикл эффекта
В отличие от обычных функций и реактивного контекста `computed`, эффекты никогда не выполняются синхронно в момент изменения сигнала. 

Если бы эффект срабатывал синхронно, это привело бы к колоссальным просадкам производительности интерфейса:
```typescript
// Симуляция множественной записи
this.count.set(1);
this.count.set(2);
this.count.set(3);
```
При синхронном подходе эффект запустился бы трижды, заставив браузер делать лишние манипуляции с DOM-деревом или сохранением данных.

Для предотвращения этой проблемы в Angular Signals встроен **Планировщик микрозадач (Microtask Scheduler)**. Когда сигнал помечает эффект как dirty, планировщик не запускает коллбэк немедленно. Он упаковывает задачу выполнения эффекта в очередь микрозадач браузера (Microtask Queue via `Promise.resolve()`). 

Когда текущий синхронный стек вызовов JavaScript полностью опустошается (происходит сборка всех изменений состояния и завершается отрисовка), планировщик извлекает эффект из очереди и выполняет его ровно один раз с итоговым стабильным состоянием данных.

### 2. Физика untracked и временный выход из реактивного контекста
Как устроена функция `untracked` под капотом компилятора Angular?

В процессе выполнения любого реактивного контекста (`computed`, `effect`) Angular устанавливает глобальную системную ссылку на текущего «активного слушателя» — **Active Consumer**. Любой сигнал, к которому обращаются в коде, видит эту ссылку и регистрирует себя в качестве зависимости у этого слушателя.

Когда интерпретатор встречает функцию `untracked(fn)`, Angular временно затирает глобальную ссылку на `Active Consumer`, устанавливая её в `null`, и только после этого выполняет вложенный коллбэк `fn`. Все сигналы, считанные внутри этого коллбэка, видят пустую ссылку, не могут зарегистрировать зависимость и завершают чтение без создания связей в реактивном графе. После успешного выполнения коллбэка Angular восстанавливает ссылку на исходного потребителя.

### 3. Пошаговый разбор жизненного цикла onCleanup
Проследим физику выполнения коллбэка очистки из Шаблона 2 при изменении интервала опроса сервера с 3000мс на 1000мс:

1.  **Действие:** Сигнал `pollingIntervalMs` переходит в значение `1000`. Версия сигнала инкрементируется.
2.  **Уведомление планировщика:** Эффект получает dirty-уведомление, планировщик ставит задачу перезапуска эффекта в очередь микрозадач.
3.  **Запуск фазы очистки:** Перед тем как заново выполнить тело эффекта, Angular обращается к кэшу предыдущей итерации этого эффекта и видит зарегистрированную функцию `onCleanup`.
4.  **Уничтожение ресурсов:** Angular синхронно выполняет код очистки: `clearInterval(timerId)`. Предыдущий таймер на 3000мс уничтожается на уровне ядра браузера.
5.  **Новый запуск:** Тело эффекта запускается с новым значением `interval = 1000`. Создается новый таймер, и его новый ID регистрируется для последующей очистки.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Прямая запись в сигналы внутри эффекта (allowSignalWrites Error)**
    *   *Симптомы:* Критическая ошибка рантайма `Writing to signals is not allowed in a computed or an effect context`.
    *   *Физика процесса:* Разработчик пытается обновить состояние другого сигнала внутри эффекта: `effect(() => { this.anotherSignal.set(1); })`. Изменение сигналов внутри эффектов по умолчанию заблокировано на уровне фреймворка. Это спроектировано для предотвращения каскадных лавинных перерисовок и бесконечных циклов обновлений в реактивном графе.
    *   *Решение:* Перепишите логику с использованием `computed` или `linkedSignal`. В крайних случаях, если запись в сигнал неизбежна и безопасна (например, установка статуса лога), можно принудительно включить её через опцию `allowSignalWrites: true`, но это считается плохой архитектурной практикой (code smell).

```typescript
// ОШИБКА: Запись заблокирована фреймворком
// effect(() => { this.logSignal.set(this.count() * 2); });

// ИСПРАВЛЕНИЕ А (Лучшее): Использование реактивных связей через computed
const doubleCount = computed(() => this.count() * 2);

// ИСПРАВЛЕНИЕ Б (Исключительное): Принудительное разрешение записи в опциях
effect(() => {
  this.logSignal.set(this.count() * 2);
}, { allowSignalWrites: true });
```

*   **Ошибка 2: Объявление эффекта вне контекста внедрения без передачи Injector**
    *   *Симптомы:* При попытке динамического создания эффекта внутри метода класса приложение падает с ошибкой `effect() can only be used within an active injection context`.
    *   *Физика процесса:* Эффекты по умолчанию требуют доступа к механизму автоматического отслеживания жизненного цикла, чтобы уничтожать себя вместе с родительским компонентом. Этот доступ предоставляется контекстом внедрения зависимостей (Injection Context), который активен в конструкторе класса. Если вы попытаетесь вызвать `effect()` внутри обычного метода (например, при клике на кнопку), Angular не сможет получить доступ к инжектору и аварийно завершит работу.
    *   *Решение:* Если эффект нужно создать динамически, сохраните корневой инжектор в конструкторе и передайте его явно в опциях конфигурации эффекта.

```typescript
// ОШИБКА: effect() вызван вне конструктора в обычном методе
// @Component(...)
// export class MyComp {
//   startTracking() { effect(() => { ... }); } 
// }

// ИСПРАВЛЕНИЕ: Передача инжектора вручную при динамическом создании
@Component(...)
export class MyComp {
  private readonly injector = inject(Injector);

  public startTracking(): void {
    effect(() => {
      console.log('Динамический эффект запущен');
    }, { injector: this.injector });
  }
}
```

*   **Ошибка 3: Наложение параллельных асинхронных процессов из-за отсутствия onCleanup**
    *   *Симптомы:* Браузер начинает сильно тормозить, в консоли дублируются запросы, асинхронные операции выполняются хаотично и накладываются друг на друга.
    *   *Физика процесса:* Разработчик вешает прослушивание событий или таймер внутри эффекта, но забывает зарегистрировать функцию очистки: `effect(() => { window.addEventListener('resize', () => { ... }) })`. При каждом изменении зависимых сигналов эффект перезапускается, вешая всё новые и новые обработчики событий на объект `window` параллельно старым.
    *   *Решение:* Всегда регистрируйте уничтожение внешних ресурсов внутри коллбэка `onCleanup`.

```typescript
// ОШИБКА: Каждая итерация эффекта будет вешать дублирующий слушатель событий
// effect(() => {
//   window.addEventListener('resize', this.handler);
// });

// ИСПРАВЛЕНИЕ: Старый слушатель гарантированно уничтожается перед созданием нового
effect((onCleanup) => {
  window.addEventListener('resize', this.handler);
  onCleanup(() => window.removeEventListener('resize', this.handler));
});
```
