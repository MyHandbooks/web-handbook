# Реактивность с использованием Signals

## БЫСТРЫЙ СТАРТ

*   **Signals (Сигналы)** — это базовые синхронные реактивные примитивы Angular, представляющие собой обертки над значениями. Они умеют автоматически отслеживать свои зависимости и точечно уведомлять фреймворк о необходимости проверки изменений (Change Detection).
*   **Декларативная экосистема:** Сигналы образуют ориентированный ациклический граф (DAG), связывающий источники данных (`signal`) с производными вычислениями (`computed`), автоматическими сбросами (`linkedSignal`), асинхронными сетевыми операциями (`resource` / `rxResource`) и побочными эффектами (`effect`).
*   **Используйте для:** организации синхронного состояния пользовательского интерфейса, реализации легких вычисляемых свойств, бесконфликтной синхронизации связанных форм и перехода к высокопроизводительной архитектуре рендеринга без Zone.js (Zoneless).
*   **Не используйте для:** обработки потоков дискретных событий реального времени (например, входящих сообщений WebSockets или частых кликов со временем) — для этих задач по-прежнему оптимально подходит библиотека RxJS.

### Шаблон 1: Архитектурный каркас сигнального хранилища компонента (Signal-Store Shell)
*   **Назначение:** Описание комплексного шаблона, демонстрирующего правильную оркестрацию и маршрутизацию всех типов сигнальных примитивов внутри современного компонента Angular 19+.

#### 1. Файл логики: `signal-orchestrator.ts`
```typescript
import { Component, ChangeDetectionStrategy, signal, computed, linkedSignal, effect, resource, inject } from '@angular/core';

export interface DataPayload {
  id: string;
  name: string;
}

@Component({
  selector: 'app-signal-orchestrator',
  // template: Разметка вынесена во внешний HTML-файл согласно стандартам
  templateUrl: './signal-orchestrator.html',
  // styleUrl: Стили вынесены во внешний CSS-файл
  styleUrl: './signal-orchestrator.css',
  // OnPush гарантирует, что компонент будет перерисовываться только при обновлении сигналов
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class SignalOrchestrator {
  // 1. Изменяемый сигнал-источник (WritableSignal) для хранения ID активного элемента
  public readonly activeId = signal<string>('id_101');

  // 2. Связанный сигнал (linkedSignal) для автоматического сброса выбранной под-опции.
  // Как только меняется activeId(), значение optionId сбрасывается к дефолтному 'default_item'.
  // При этом мы можем свободно вызывать на нем метод .set() для ручной перезаписи пользователем.
  public readonly optionId = linkedSignal<string, string>({
    source: this.activeId,
    computation: (currentId) => `default_for_${currentId}`
  });

  // 3. Вычисляемый сигнал (computed) для декларативного расчета производных данных.
  // Кэшируется в памяти, пересчет сработает только при изменении activeId() или optionId().
  public readonly displayLabel = computed<string>(() => {
    return `Активен: ${this.activeId().toUpperCase()} -> Опция: ${this.optionId()}`;
  });

  // 4. Асинхронный ресурс (resource API) для декларативной сетевой загрузки.
  // Запрос в loader запускается автоматически при изменении реактивных параметров params().
  public readonly dataResource = resource<DataPayload, string>({
    params: () => this.activeId(),
    loader: ({ params: id, abortSignal }) => {
      const api = `https://api.enterprise-service.com/v1/data/${id}`;
      return fetch(api, { signal: abortSignal }).then((res) => {
        if (!res.ok) throw new Error('Не удалось получить данные');
        return res.json() as Promise<DataPayload>;
      });
    }
  });

  constructor() {
    // 5. Побочный эффект (effect) для синхронизации состояния со сторонними API
    effect(() => {
      const currentLabel = this.displayLabel();
      // Выполняем запись в логгер или localStorage (побочный эффект)
      console.log(`[Reactivity Graph] Состояние обновлено: ${currentLabel}`);
    });
  }

  public switchId(nextId: string): void {
    // Метод set() пометит зависимых потребителей грязными (dirty)
    this.activeId.set(nextId);
  }

  public changeOptionManual(newOption: string): void {
    // linkedSignal разрешает ручное изменение значения пользователем
    this.optionId.set(newOption);
  }
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Push-Pull модель реактивности против Push-модели RxJS (Glitch-Free)
Традиционная реактивность в Angular на базе библиотеки RxJS (потоки `Observable` и `BehaviorSubject`) работает по чистой **Push-модели (проталкивание)**. Когда значение в источнике изменяется, оно насильно проталкивается вниз по всей цепочке операторов к конечным подписчикам. 

Если у вас есть сложный граф зависимостей, напоминающий ромб (Diamond Dependency):

```text
       [ Сигнал-источник А ] (Producer)
           /         \
          ▼           ▼
     [ Стрим Б ]    [ Стрим В ]
          \           /
           ▼         ▼
       [ Результирующее Г ] (Consumer)
```

В Push-модели при изменении `А` результирующий узел `Г` может выполниться дважды: сначала когда долетит обновление от `Б` (но в `В` еще будет находиться старое значение), а затем когда долетит обновление от `В`. Это создает кратковременное мерцание (глитч) некорректных данных на экране и паразитную нагрузку на процессор.

Сигналы Angular решают эту проблему за счет **Push-Pull модели (уведомление + ленивое стягивание)**:
1.  **Phase 1: Push (Уведомление):** Когда меняется значение сигнала `А`, он не запускает вычисления. Он лишь отправляет по ориентированному ациклическому графу (DAG) наверх короткое синхронное dirty-уведомление: *«Внимание, мои зависимости изменились, я грязный»*. Все связанные потребители помечаются флагом `dirty`.
2.  **Phase 2: Pull (Стягивание):** Перевычисление происходит лениво. Только тогда, когда Angular реально собирается перерисовать экран или когда код обращается к значению вычисляемого сигнала `Г()`, потребитель запускает топологический обход графа, стягивает актуальные значения от `Б` и `В` и производит расчет **ровно один раз**, полностью исключая глитчи (Glitch-Free) и лишние такты процессора.

### 3. Роль Сигналов в Zoneless-архитектуре
До появления Сигналов автоматический Change Detection в Angular держался на библиотеке `zone.js`, которая перехватывала абсолютно все асинхронные события в браузере (таймеры, клики, сетевые запросы) и заставляла Angular запускать проверку изменений **всего дерева компонентов с самого верха до самого низа**, обходя сотни узлов.

В современной Zoneless-архитектуре (`provideExperimentalZonelessChangeDetection()`) библиотека `zone.js` полностью исключается из бандла. Процесс проверки изменений переходит на точечную реактивность:
*   Когда сигнал считывается в шаблоне компонента, Angular регистрирует этот компонент как потребителя.
*   При изменении сигнала dirty-уведомление помечает только этот конкретный узел дерева как требующий проверки.
*   Планировщик Angular запускает точечный рендеринг строго для помеченных `dirty` компонентов на следующем микрошаге браузера, экономя до 99% холостых циклов процессора.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Ошибка циклической зависимости при попытке записи в сигналы внутри `computed`**
    *   *Симптомы:* Критическая рантайм-ошибка: `NG0600: Circular dependency in computed queries...` или бесконечный цикл зависания вкладки браузера.
    *   *Физика процесса:* Разработчик пытается выполнить побочное действие (Side Effect) — вызвать метод записи `.set()` или `.update()` у другого сигнала внутри формулы `computed`: `computed(() => { this.state.set(1); })`. Поскольку вычисления происходят во время фазы чтения графа, запись в этот момент нарушает топологический порядок обхода и приводит к зацикливанию.
    *   *Решение:* Вычисляемые сигналы `computed` должны оставаться строго чистыми (pure) функциями, выполняющими только чтение и возврат значения. Все побочные эффекты выносите в обработчики событий или эффекты `effect()`.

*   **Ошибка 2: Ложная реактивность при чтении обычных переменных класса**
    *   *Симптомы:* Обычная переменная изменилась, но вычисляемый сигнал или шаблон не реагируют на это изменение и продолжают отображать старые данные.
    *   *Физика процесса:* Разработчик использует обычную переменную внутри `computed` или шаблона: `total = computed(() => this.count() * this.multiplier)`. Обычные переменные не имеют механизмов отправки dirty-уведомлений. `computed` пересчитается только при изменении сигнала `count()`. Если изменится только `multiplier`, вычисляемый сигнал вернет старое закэшированное значение из памяти.
    *   *Решение:* Все переменные, изменение которых должно приводить к обновлению интерфейса, должны быть объявлены как реактивные сигналы.

*   **Ошибка 3: Утечки памяти из-за ручного неконтролируемого создания эффектов**
    *   *Симптомы:* Медленный рост потребления памяти (Memory Leak) и многократное дублирование выполнения логики эффектов.
    *   *Физика процесса:* Разработчик создает эффект `effect()` динамически внутри обычного метода класса (например, при клике на кнопку), не передавая в него инжектор. Это приводит к лавинообразному размножению активных эффектов в памяти, так как Angular не может автоматически привязать их к жизненному циклу компонента.
    *   *Решение:* Объявляйте эффекты строго на уровне конструктора класса (в активном Injection Context). Если динамическое создание необходимо, сохраняйте ссылку на `Injector` в конструкторе и явно передавайте её в опциях конфигурации эффекта: `effect(() => { ... }, { injector: this.injector })`.
