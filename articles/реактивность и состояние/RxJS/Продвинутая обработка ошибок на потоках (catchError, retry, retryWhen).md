# Продвинутая обработка ошибок на потоках (catchError, retry, retryWhen)

## БЫСТРЫЙ СТАРТ

*   **Терминальная природа ошибок:** По спецификации RxJS, сигнал ошибки (`error`) является финальным событием потока. Как только поток сгенерировал ошибку, он **навсегда умирает** — подписка аннулируется, и поток больше не может испустить ни одного значения.
*   **Два ключевых оператора:**
    *   `catchError(callback)` — перехватывает сигнал ошибки и позволяет "погасить" её, вернув новый резервный поток (например, `of(fallbackValue)`), либо пробросить отформатированную ошибку дальше через `throwError`.
    *   `retry({ count, delay })` — при возникновении сбоя автоматически отписывается от упавшего источника и осуществляет повторную подписку (*re-subscribe*), заставляя запустить асинхронную операцию заново.
*   **Важная деградация (Deprecation):** Классический оператор `retryWhen` официально признан **устаревшим** в RxJS 7/8. Вместо него настоятельно рекомендуется использовать унифицированную конфигурацию оператора `retry({ delay: (error, count) => Observable })`.
*   **Используйте для:** изоляции ошибок внутри вложенных сетевых потоков (чтобы сбой одного запроса не ломал главную поисковую строку) и построения умных стратегий повторов (Exponential Backoff).
*   **Не используйте:** для простых синхронных проверок валидации (для этого достаточно стандартного `filter` или JS-инструкции `throw` внутри `map`).

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Изоляция сетевой ошибки во вложенном потоке (Inner Stream Recovery)
*   **Назначение:** Реализация поисковой строки, которая продолжает стабильно функционировать и принимать ввод пользователя, даже если один из сетевых запросов завершился ошибкой `500`.

```typescript
import { Component, inject, OnInit, signal, DestroyRef } from '@angular/core';
import { FormControl, ReactiveFormsModule } from '@angular/forms';
import { HttpClient } from '@angular/common/http';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { of } from 'rxjs';
import { debounceTime, distinctUntilChanged, switchMap, catchError } from 'rxjs/operators';

@Component({
  selector: 'app-safe-search',
  standalone: true,
  imports: [ReactiveFormsModule],
  template: `
    <div class="search-card">
      <input type="text" [formControl]="searchControl" placeholder="Поиск..." />
    </div>
  `
})
export class SafeSearchComponent implements OnInit {
  private readonly http = inject(HttpClient);
  private readonly destroyRef = inject(DestroyRef);

  public readonly searchControl = new FormControl<string>('', { nonNullable: true });

  public ngOnInit(): void {
    this.searchControl.valueChanges.pipe(
      debounceTime(300),
      distinctUntilChanged(),
      // switchMap переключает нас на внутренний асинхронный HTTP-поток
      switchMap((term) => {
        const url = `/api/v1/search?q=${term}`;
        
        return this.http.get<string[]>(url).pipe(
          // КРИТИЧЕСКИ ВАЖНО: catchError размещается строго ВНУТРИ switchMap.
          // Если сетевой запрос упадет, catchError погасит ошибку, вернет пустой массив [].
          // Внутренний поток успешно завершится, но ВНЕШНИЙ поток valueChanges останется жив!
          catchError((err: Error) => {
            console.error('[Search] Сбой сетевого запроса, гасим ошибку:', err.message);
            return of([]); // Возвращаем безопасный пустой массив
          })
        );
      }),
      takeUntilDestroyed(this.destroyRef)
    ).subscribe({
      next: (data) => console.log('[UI] Данные получены:', data),
      // Этот коллбэк error никогда не будет вызван при сбоях сети, так как ошибки изолированы
      error: (err) => console.error('[UI] Критическая смерть главного потока ввода!', err)
    });
  }
}
```

### Шаблон 2: Экспоненциальный повтор запросов на современном `retry()` (RxJS 7+)
*   **Назначение:** Описание умного повтора сетевых запросов при временной потере связи с прогрессирующим интервалом ожидания и блокировкой повторов для заведомо ложных статусов (401, 404).

```typescript
import { Injectable, inject } from '@angular/core';
import { HttpClient, HttpErrorResponse } from '@angular/common/http';
import { Observable, timer, throwError } from 'rxjs';
import { retry, catchError } from 'rxjs/operators';

@Injectable({
  providedIn: 'root'
})
export class RecoveryService {
  private readonly http = inject(HttpClient);

  public loadConfigData(): Observable<unknown> {
    return this.http.get<unknown>('/api/v1/config').pipe(
      // Используем современную сигнатуру retry с функцией-фабрикой delay
      retry({
        count: 3, // Максимум 3 попытки
        delay: (error: HttpErrorResponse, retryCount: number): Observable<number> => {
          // Если ошибка на стороне клиента (401 Unauthorized или 404 Not Found) — 
          // повторные запросы бессмысленны. Сразу пробрасываем ошибку дальше, прерывая retry.
          if (error.status === 401 || error.status === 404) {
            throw error;
          }

          // Вычисляем экспоненциальную задержку: 1-я попытка — 1с, 2-я — 2с, 3-я — 4с
          const backoffDelay = Math.pow(2, retryCount - 1) * 1000;
          console.warn(`[Retry] Сбой. Попытка №${retryCount}. Перезапуск через ${backoffDelay}мс.`);
          
          // Возвращаем таймер. Когда он сработает, retry выполнит повторную подписку
          return timer(backoffDelay);
        }
      })
    );
  }
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Физика терминальной ошибки и защита Главной Шины (Event Bus)
Когда в потоке возникает ошибка, RxJS-источник вызывает внутренний метод `observer.error(err)`. Согласно спецификации:
1.  Уведомление об ошибке передается вниз по цепочке операторов.
2.  Выполняется экстренная отписка (*unsubscribe*) текущего клиента.
3.  Поток переходит в статус закрытого. Физический канал связи уничтожается.

Если вы подписали форму ввода на события клавиатуры, и сетевой запрос внутри цепочки упал, необработанная ошибка поднимется до самого верха и уничтожит подписку на инпут. Форма перестанет реагировать на ввод букв навсегда.

Чтобы этого не произошло, применяется паттерн **Изоляции ошибок во вложенном потоке (Inner Stream Recovery)**. Мы переносим обработку сетевого запроса внутрь операторов высшего порядка (`switchMap`, `mergeMap`, `concatMap`) и вешаем `catchError` **строго на внутренний сетевой поток** (Шаблон 1). Сетевая ошибка гасится внутри, возвращая успешное значение (например, `of([])`). Внешний поток-инициатор видит лишь успешный приход пустого массива и продолжает стабильно жить.

### 2. Почему RxJS 7 депрецировал `retryWhen`
В старых версиях RxJS для реализации сложной логики повторов с задержками использовался оператор `retryWhen`:
```typescript
// УСТАРЕВШИЙ И СЛОЖНЫЙ ПОДХОД (RxJS v6)
source$.pipe(
  retryWhen(errors$ => errors$.pipe(delay(1000)))
);
```
Этот подход имел две серьезные архитектурные проблемы:
1.  **Сложность понимания контекста:** `retryWhen` принимал поток ошибок `errors$`. Разработчикам приходилось городить сложные конструкции с замыканиями, индексами попыток (`scan`) и объединением данных, чтобы понять, какая именно ошибка произошла на текущем шаге.
2.  **Утечки памяти и проблемы с замыканиями:** Поток `errors$` жил своей жизнью, что часто приводило к утечкам подписок при некорректном связывании.

В современных стандартах RxJS 7/8 оператор `retry` был полностью переработан. Теперь он принимает объект параметров, где свойство `delay` может быть как простым числом, так и функцией-фабрикой `(error, retryCount) => Observable`. Это полностью искоренило необходимость в использовании `retryWhen`, объединив всю логику повторов в один понятный и безопасный C++ оптимизированный контракт.

### 3. Детальный пошаговый разбор выполнения шаблона 1
Проследим шаги прохождения ошибки при вводе текста:
1.  **Действие:** Пользователь вводит текст. Поток `valueChanges` испускает строку.
2.  **Запуск лоадера:** Оператор `switchMap` перехватывает строку и подписывается на внутренний поток `http.get('/search')`.
3.  **Сбой сервера:** Сервер возвращает ошибку `500 Internal Server Error`.
4.  **Перехват в `catchError`:** Локальный оператор `catchError`, висящий прямо на `http.get()`, перехватывает `HttpErrorResponse`.
5.  **Гашение ошибки:** Коллбэк внутри `catchError` возвращает `of([])`. Поток `http.get()` успешно гасит ошибку и завершается с единственным значением `[]`.
6.  **Результат во внешнем потоке:** Оператор `switchMap` получает на вход чистый массив `[]`, не видя никакой ошибки. Массив передается в `.subscribe({ next })`. Главный поток ввода продолжает активно слушать изменения клавиатуры.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Размещение `catchError` на внешнем потоке вместо внутреннего**
    *   *Симптомы:* Поисковая строка полностью ломается и перестает реагировать на ввод пользователя после первой же ошибки сервера.
    *   *Причина:* Разработчик повесил `catchError` на внешний поток, идущий после `switchMap`:
        ```typescript
        // ОШИБКА: Ошибка из switchMap поднимется наверх и убьет поток valueChanges!
        this.control.valueChanges.pipe(
          switchMap(t => this.http.get(url)),
          catchError(err => of([])) // ! Поток valueChanges уничтожен!
        ).subscribe();
        ```
    *   *Решение:* Перенесите `catchError` внутрь трубы (`pipe()`) самого сетевого запроса внутри `switchMap` (как показано в Шаблоне 1).

*   **Ошибка 2: Бесконечные повторы запросов авторизации или отсутствующих страниц**
    *   *Симптомы:* Сетевой шлюз перегружается бесконечными цикличными запросами к API при падении сервера.
    *   *Причина:* Использование оператора `retry` без фильтрации статус-кодов ошибок. Например, если запрос падает со статусом `404 Not Found` или `401 Unauthorized`, повторный автоматический перезапрос гарантированно завершится тем же сбоем, бессмысленно забивая трафик клиента и нагружая процессор.
    *   *Решение:* Внутри фабрики `delay` оператора `retry` всегда делайте жесткую проверку статус-кодов. Если статус указывает на клиентскую ошибку (400, 401, 403, 404), прерывайте цепочку повторов путем мгновенного выброса ошибки через `throw error` (как показано в Шаблоне 2).

*   **Ошибка 3: Возврат не-Observable значения из `catchError`**
    *   *Симптомы:* Ошибка компиляции TypeScript вида `Type 'null' is not assignable to type 'ObservableInput<any>'` или падение рантайма.
    *   *Физика процесса:* Разработчик пытается вернуть из `catchError` сырой объект или `null` напрямую: `catchError(err => null)`. По спецификации `catchError` обязан возвращать только валидный реактивный источник данных (**`ObservableInput`**), например, созданный через `of(null)` или `EMPTY`.
    *   *Решение:* Оборачивайте любые дефолтные возвращаемые объекты в вызов оператора `of()` или возвращайте пустой поток `EMPTY`.

```typescript
// ОШИБКА: Возврат сырого значения приведет к краху компиляции
// catchError(err => ({ data: [] })) 

// ИСПРАВЛЕНИЕ: Обертывание в реактивный источник of()
catchError(err => of({ data: [] }))
```
