# Совместное использование потоков (shareReplay)

## БЫСТРЫЙ СТАРТ

*   **Оператор `shareReplay`** — специализированный инструмент RxJS, предназначенный для преобразования «холодного» потока данных в «горячий» (мультикастинговый) с возможностью кэширования последнего испущенного значения (или нескольких значений) и его мгновенного повторения (replay) новым подписчикам.
*   **Искоренение дублирования запросов:** По умолчанию каждая новая подписка (например, несколько директив `async` в HTML-шаблоне) на один и тот же холодный поток HTTP-запроса заставит Angular совершить отдельный, дублирующий физический сетевой вызов к API. `shareReplay` перехватывает этот процесс: выполняется ровно один сетевой запрос, а его результат раздается всем подписчикам совместно из локального кэша в памяти.
*   **Правила использования:**
    *   **Используйте:** Для кэширования тяжелых и редко меняющихся сетевых данных (справочники, словари, списки стран/валют, конфигурации приложения, профиль текущего пользователя), а также для совместного использования результатов сложных вычислений в разных частях экрана.
    *   **Не используйте:** Для динамических транзакционных запросов, где на каждую подписку всегда требуются 100% свежие сетевые данные, или для методов модификации (POST, PUT, DELETE).

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Кэширующий сервис статических справочников
*   **Назначение:** Реализация надежного глобального сервиса, который один раз запрашивает массив стран с сервера и раздает его всем компонентам из кэша, полностью блокируя повторные сетевые вызовы.

```typescript
import { Injectable, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { shareReplay, catchError } from 'rxjs/operators';

export interface CountryDictionary {
  code: string;
  name: string;
}

@Injectable({
  providedIn: 'root'
})
export class DictionaryService {
  private readonly http = inject(HttpClient);
  private readonly api = 'https://api.enterprise-service.com/v1/dictionaries/countries';

  // Объявляем поток-источник. Пока на него никто не подписался, запрос в сеть не уходит.
  // Используем современную конфигурацию shareReplay с объектом параметров.
  public readonly countries$: Observable<CountryDictionary[]> = this.http.get<CountryDictionary[]>(this.api).pipe(
    shareReplay({
      bufferSize: 1,   // Кэшируем ровно 1 последнее значение
      refCount: true   // Важнейший флаг автоматической отписки при отсутствии активных слушателей
    }),
    // Гасим ошибку на случай падения сервера, возвращая пустой массив
    catchError((err: Error) => {
      console.error('[Dictionary] Критическая ошибка загрузки справочника:', err);
      throw err;
    })
  );
}
```

### Шаблон 2: Совместное использование потока в шаблоне (Несколько AsyncPipe)
*   **Назначение:** Пример UI-компонента, который выводит информацию об одном и том же потоке данных в разных независимых блоках верстки без дублирования HTTP-запросов к бэкенду.

```typescript
import { Component, inject } from '@angular/core';
import { AsyncPipe, JsonPipe } from '@angular/common';
import { DictionaryService } from './dictionary.service';

@Component({
  selector: 'app-country-selector',
  standalone: true,
  imports: [AsyncPipe, JsonPipe],
  template: `
    <div class="selector-card">
      <!-- Блок 1: Выводим количество стран -->
      <div class="info-header">
        @if (countries$ | async; as list) {
          <p>Загружено стран: {{ list.length }}</p>
        } @else {
          <p>Загрузка справочника...</p>
        }
      </div>

      <!-- Блок 2: Выводим выпадающий список -->
      <div class="info-body">
        <select>
          <!-- Благодаря shareReplay, эта вторая подписка async НЕ совершит повторный HTTP-запрос! -->
          @for (country of countries$ | async; track country.code) {
            <option [value]="country.code">{{ country.name }}</option>
          }
        </select>
      </div>
    </div>
  `
})
export class CountrySelectorComponent {
  private readonly dictionaryService = inject(DictionaryService);

  // Передаем ссылку на кэшируемый поток напрямую в шаблон
  public readonly countries$ = this.dictionaryService.countries$;
}
```

### Шаблон 3: Механизм принудительного сброса (инвалидации) кэша shareReplay
*   **Назначение:** Описание паттерна с использованием переключателя `Subject` для возможности принудительного сброса кэша и повторной отправки запроса по требованию пользователя.

```typescript
import { Injectable, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable, Subject, merge } from 'rxjs';
import { shareReplay, switchMap } from 'rxjs/operators';

@Injectable({
  providedIn: 'root'
})
export class ConfigurationCacheService {
  private readonly http = inject(HttpClient);
  private readonly api = 'https://api.enterprise-service.com/v1/config';

  // Триггер для ручного сброса кэша
  private readonly refreshCache$ = new Subject<void>();

  // Публичный поток, объединяющий авто-инициализацию и триггер ручного сброса
  public readonly appConfig$: Observable<unknown> = merge(
    // Стартуем сразу при первом обращении
    of(null),
    // А также принудительно перезапускаем при вызове refreshCache$
    this.refreshCache$
  ).pipe(
    // switchMap отменит старый запрос и запустит свежий при срабатывании триггера
    switchMap(() => this.http.get<unknown>(this.api)),
    // Совместно используем и кэшируем результат
    shareReplay({ bufferSize: 1, refCount: true })
  );

  /**
   * Инициирует принудительный сброс кэша и перезапрос данных с сервера
   */
  public invalidateCache(): void {
    console.warn('[Cache] Сигнал сброса кэша конфигурации получен. Делаем повторный запрос.');
    this.refreshCache$.next();
  }
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Архитектурная физика холодных и горячих потоков (Cold vs Hot Observables)
Понимание физики потоков RxJS — ключ к написанию производительных enterprise-приложений:

*   **Холодные потоки (Cold):** Ведут себя лениво. Код-производитель (например, отправка запроса `HttpClient`) запускается заново для каждого нового подписчика. Если в шаблоне написано 3 пайпа `async` для одного и того же Observable, Angular под капотом вызовет `.subscribe()` 3 раза, и браузер отправит 3 идентичных параллельных HTTP-запроса на бэкенд.
*   **Горячие потоки (Hot):** Ведут себя как радиовещание. Источник активен сам по себе и передает данные всем слушателям одновременно. Все подписчики делят между собой одну единственную точку выполнения.

Оператор `shareReplay` выступает в роли реактивного прокси-сервера (Proxy) внутри конвейера. Он оформляет **ровно одну** подписку на ваш холодный сетевой запрос, перехватывает полученный ответ, сохраняет его в своем внутреннем буфере в куче памяти (Heap) и транслирует эту готовую копию ответа всем настоящим подписчикам.

### 2. Эволюция shareReplay и критическая важность настройки refCount
В ранних версиях RxJS (v5/v6) существовала серьезная проблема утечек памяти при вызове оператора по старой упрощенной сигнатуре: `shareReplay(1)`. 

При такой записи параметр `refCount` по умолчанию принимал значение `false`. Это приводило к следующей физике процесса:
*   Когда первый компонент подписывался на поток, `shareReplay` создавал подписку на сетевой источник.
*   Когда все компоненты уничтожались (например, пользователь ушел с экрана), количество активных подписчиков падало до `0`.
*   При `refCount: false` оператор `shareReplay` **не отписывался** от исходного потока! Он продолжал удерживать вечную активную связь с источником в фоновом режиме, забивая память и не позволяя Garbage Collector очистить связанные структуры.

В современном RxJS 7/8 строго рекомендуется использовать конфигурацию с явным флагом `{ refCount: true }`. Этот флаг инструктирует оператор: *«Как только количество активных подписчиков упадет до 0, немедленно отпишись от исходного сетевого потока и полностью очисти буфер кэша в памяти»*. Это гарантирует надежную защиту от утечек памяти при переходах между страницами.

### 3. Пошаговый разбор жизненного цикла кэшируемого запроса
Проследим выполнение цепочки в `DictionaryService` (Шаблон 1) при обращении разных компонентов:

1.  **Компонент А открывается:** Шаблон компонента А подписывается через `countries$ | async`.
2.  **Сетевой вызов:** `shareReplay` видит первого подписчика (количество слушателей переходит с `0` на `1`). Он инициирует физический HTTP-запрос `countries`.
3.  **Приход ответа:** Сервер возвращает массив стран через 300мс.
4.  **Кэширование:** `shareReplay` сохраняет массив во внутреннем буфере `bufferSize: 1` и отправляет его в компонент А.
5.  **Компонент Б открывается:** Через 2 секунды на другом экране открывается компонент Б, требующий тот же справочник. Он подписывается на `countries$`.
6.  **Мгновенная выдача (Replay):** `shareReplay` видит нового подписчика, но **не делает сетевой запрос**. Он мгновенно синхронно извлекает сохраненный массив из буфера памяти и передает его компоненту Б.
7.  **Закрытие экранов:** Оба компонента закрываются. Количество подписчиков падает до `0`. Благодаря `refCount: true`, `shareReplay` завершает подписку, высвобождая память. При следующем открытии экрана запрос выполнится заново.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Бесконечное удержание кэша при отсутствии refCount (Memory Leak / Stale Data)**
    *   *Симптомы:* Медленный рост потребления памяти вкладкой браузера, а данные справочников никогда не обновляются на клиенте, даже если администратор изменил их на бэкенде.
    *   *Физика процесса:* Разработчик использовал устаревший синтаксис `shareReplay(1)`. Поток никогда не отписывается от источника, кэш намертво застревает в памяти браузера до полной ручной перезагрузки страницы пользователем.
    *   *Решение:* Всегда передавайте конфигурационный объект `{ bufferSize: 1, refCount: true }`.

```typescript
// ОШИБКА: Опасность утечки памяти и вечного зависания кэша в памяти
// return this.http.get(url).pipe(shareReplay(1));

// ИСПРАВЛЕНИЕ: Автоматическое уничтожение кэша при уходе всех подписчиков
return this.http.get(url).pipe(
  shareReplay({ bufferSize: 1, refCount: true })
);
```

*   **Ошибка 2: Кэширование сетевых ошибок (Dead Cache Bug)**
    *   *Симптомы:* Запрос к справочнику упал из-за кратковременного сбоя сети. При последующих переходах пользователя на этот экран справочник отображает ошибку мгновенно, не пытаясь сделать повторный запрос к восстановившемуся серверу.
    *   *Физика процесса:* Если сетевой запрос завершается ошибкой `HttpErrorResponse`, `shareReplay` по умолчанию кэширует этот сигнал ошибки (`error notification`). Любой новый подписчик будет мгновенно получать этот сохраненный сигнал ошибки из буфера без повторной попытки сетевого запроса.
    *   *Решение:* Добавляйте обработку ошибок или операторы авто-повтора *до* вызова `shareReplay`, либо настраивайте инвалидацию кэша (как в Шаблоне 3).

```typescript
// ОШИБКА: Ошибка сервера запишется в кэш и будет вечно транслироваться подписчикам
// return this.http.get(url).pipe(shareReplay({ bufferSize: 1, refCount: true }));

// ИСПРАВЛЕНИЕ: Изоляция ошибки с возвратом дефолтного значения до кэширования
return this.http.get(url).pipe(
  catchError(() => of([])), // Гарантирует, что в кэш запишется чистый пустой массив вместо ошибки
  shareReplay({ bufferSize: 1, refCount: true })
);
```

*   **Ошибка 3: Использование shareReplay для неидемпотентных POST/PUT запросов**
    *   *Симптомы:* Пользователь пытается создать несколько разных заказов подряд, но в базу данных отправляется только первый заказ, а на все последующие клики система возвращает один и тот же старый ID первого созданного заказа.
    *   *Физика процесса:* Разработчик ошибочно повесил `shareReplay` на метод POST-создания заказа. Первый клик инициировал отправку пакета на сервер, сервер создал заказ и вернул его ID. `shareReplay` закэшировал этот ID. При втором клике система подписалась на поток заново, но вместо реального сетевого вызова `shareReplay` мгновенно выдал закэшированный старый ID из памяти.
    *   *Решение:* Применяйте `shareReplay` строго на безопасных операциях чтения (GET-запросы статических справочников). Любые модификации должны выполняться без кэширования.
