# Конструирование асинхронного Promise

## БЫСТРЫЙ СТАРТ

*   **Промис (`Promise`)** — это специальный объект-обертка для управления результатом асинхронной операции, которая завершится успешно или с ошибкой в будущем.
*   **Исполнитель (Executor)** — функция `(resolve, reject) => {}`, передаваемая в конструктор, которая выполняется **синхронно и немедленно** в момент создания объекта `Promise`.
*   **Используйте промисы для:** перевода асинхронных операций старого формата (события, колбэки) в современный декларативный интерфейс.
*   **Не используйте:** конструктор `new Promise` там, где данные уже доступны. Для этого есть мгновенно выполняемые методы `Promise.resolve(data)` и `Promise.reject(error)`.

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Обертывание отложенной операции (Таймера)
*   **Назначение:** Превращение классического асинхронного макротаска `setTimeout` в современный управляемый поток промиса.

```typescript
export interface TargetPayload {
  identifier: string;
  statePayload: string;
}

export function delayExecution(duration: number, payload: TargetPayload): Promise<TargetPayload> {
  // Конструктор создает новый объект промиса. Функция-исполнитель запускается немедленно
  return new Promise<TargetPayload>((resolve, reject) => {
    if (duration < 0) {
      // Переводим промис в состояние rejected при некорректных аргументах
      reject(new Error("Критическая ошибка: Задержка не может быть отрицательной."));
      return; // Прерываем выполнение исполнителя
    }

    // Регистрируем макрозадачу в Web APIs браузера
    setTimeout(() => {
      // Переводим промис в состояние fulfilled и передаем данные подписчикам
      resolve(payload); 
    }, duration);
  });
}
```

### Шаблон 2: Промисификация событийного API (FileReader)
*   **Назначение:** Обертывание асинхронных операций, основанных на событийной модели (Event Listeners), в единую цепочку промисов.

```typescript
export function readBlobAsText(blob: Blob): Promise<string> {
  return new Promise<string>((resolve, reject) => {
    const reader = new FileReader();

    // Регистрируем успешное разрешение промиса при событии загрузки
    reader.onload = () => {
      resolve(reader.result as string);
    };

    // Регистрируем ошибку при сбое чтения файла
    reader.onerror = () => {
      reject(new Error("Не удалось прочитать переданный массив бинарных данных."));
    };

    // Запускаем асинхронное чтение файла
    reader.readAsText(blob);
  });
}
```

### Шаблон 3: Быстрое создание выполненных промисов (resolve / reject)
*   **Назначение:** Возвращение готовых асинхронных ответов без вызова конструктора и накладных расходов на создание исполнителя (удобно для кэшей).

```typescript
export interface ConfigOptions {
  activeUrl: string;
}

export class ConfigCacheHolder {
  private cache = new Map<string, ConfigOptions>();

  public fetchConfig(key: string): Promise<ConfigOptions> {
    const cached = this.cache.get(key);

    if (cached) {
      // Возвращаем мгновенно выполненный промис, не создавая новый конструктор
      return Promise.resolve(cached); 
    }

    if (!key) {
      // Возвращаем мгновенно отклоненный промис при невалидном ключе
      return Promise.reject(new Error("Ключ конфигурации не задан."));
    }

    // Симуляция обращения к реальной сети в случае отсутствия данных в кэше
    const fakeFetchedConfig: ConfigOptions = { activeUrl: "https://api.eltex.co" };
    this.cache.set(key, fakeFetchedConfig);
    
    return Promise.resolve(fakeFetchedConfig);
  }
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Жизненный цикл состояний Promise
Объект `Promise` спроектирован по принципу конечного автомата. Он имеет строго три скрытых внутренних состояния:
1.  **`pending` (ожидание):** Исходное состояние. Асинхронная операция еще не завершена.
2.  **`fulfilled` (выполнено успешно):** Состояние успешного завершения. Возникает при вызове колбэка `resolve(value)`. Внутренний результат промиса заполняется значением `value`.
3.  **`rejected` (выполнено с ошибкой):** Состояние сбоя. Возникает при вызове `reject(error)` или при возникновении необработанного исключения (`throw`) внутри функции-исполнителя. Внутренний результат заполняется объектом ошибки `error`.

**Важнейшее правило иммутабельности состояний:**
Переход состояния возможен только один раз: из `pending` в `fulfilled`, либо из `pending` в `rejected`. Как только промис перешел в конечное состояние (стал *settled*), он навсегда «замораживается». Любые последующие вызовы `resolve` или `reject` внутри исполнителя будут полностью проигнорированы движком.

### 2. Спецификация микрозадач и планирование очередей
Когда промис переходит в состояние *settled* (выполнен или отклонен), его обработчики (колбэки, переданные в `.then()`, `.catch()`, `.finally()`) не выполняются немедленно. 

Интерпретатор JavaScript помещает эти колбэки в **Очередь микрозадач (Microtask Queue)**:
*   Очередь микрозадач имеет наивысший приоритет выполнения по сравнению с очередью макрозадач (таймеры, события мыши, рендеринг).
*   Как только текущий синхронный код в стеке вызовов (Call Stack) завершается, событийный цикл (Event Loop) блокирует выполнение любых макрозадач и отрисовку экрана до тех пор, пока очередь микрозадач не будет полностью опустошена.
*   Именно поэтому асинхронные цепочки промисов выполняются быстрее, чем таймеры `setTimeout(..., 0)`.

### 3. Детальный пошаговый разгон выполнения шаблона 1
1.  **Синхронный запуск:** Вызывается функция `delayExecution(100, payload)`. Внутри создается `new Promise`.
2.  **Выполнение исполнителя:** Колбэк-исполнитель `(resolve, reject) => { ... }` запускается движком V8 синхронно в том же кадре стека. 
3.  **Регистрация макрозадачи:** Инструкция `setTimeout` регистрирует таймер на 100 мс в Web APIs браузера. Промис возвращается вызывающему коду в состоянии `pending`.
4.  **Срабатывание таймера:** Спустя 100 мс таймер срабатывает, и его колбэк помещается в очередь макрозадач. При его выполнении вызывается метод `resolve(payload)`.
5.  **Планирование микрозадачи:** Промис меняет статус на `fulfilled`. Все функции, зарегистрированные на этот промис через `.then()`, упаковываются в микрозадачи и отправляются в `Microtask Queue` для выполнения при первой разгрузке стека.

### 4. Типичные ошибки и их решение

*   **Ошибка 1: Потеря возвращаемого значения внутри цепочки `.then()`**
    *   *Проблема:* Разработчик строит цепочку `.then()`, но внутри одного из звеньев забывает написать ключевое слово `return`. В результате следующее звено цепочки получает на вход `undefined`.
    *   *Причина:* Метод `.then()` всегда возвращает новый промис. Если обработчик внутри `.then()` не возвращает значение явно, возвращаемый промис автоматически разрешается значением `undefined`.
    *   *Решение:* Всегда пишите `return` для передачи данных следующему звену или для возврата вложенного промиса.

```typescript
// ПЛОХО (Второй .then получит undefined на вход)
export function runUnsafeChain(): void {
  delayExecution(100, { identifier: "id", statePayload: "start" })
    .then(data => {
      const updated = { ...data, statePayload: "modified" };
      // Забыли написать return!
    })
    .then(result => {
      // console.log(result.statePayload); // ! TypeError: Cannot read properties of undefined
    });
}

// ХОРОШО (Строгий возврат данных по всей цепочке)
export function runSafeChain(): void {
  delayExecution(100, { identifier: "id", statePayload: "start" })
    .then(data => {
      return { ...data, statePayload: "modified" }; // Явный возврат
    })
    .then(result => {
      console.log(result.statePayload); // Успешно выведет: "modified"
    });
}
```

*   **Ошибка 2: Бесконечное зависание промиса в состоянии `pending`**
    *   *Проблема:* Разработчик пишет сложный асинхронный исполнитель, но при возникновении некоторых условий (например, в блоках `if/else`) забывает вызвать `resolve()` или `reject()`. Промис зависает в памяти навсегда, а привязанный к нему UI-лоадер бесконечно крутится.
    *   *Решение:* Проектируйте код исполнителя так, чтобы при любых ветвлениях логики гарантированно вызывался либо `resolve()`, либо `reject()`, либо ограничивайте время ожидания через тайм-аут (Race-паттерн).

```typescript
// ПЛОХО (Если flag равен false, промис никогда не разрешится)
export function createHangingPromise(flag: boolean): Promise<string> {
  return new Promise<string>((resolve, reject) => {
    if (flag) {
      resolve("success_status");
    }
    // Забыли ветку else: при flag === false промис вечно висит в состоянии pending!
  });
}
```

*   **Ошибка 3: Создание тяжелых синхронных вычислений внутри исполнителя**
    *   *Проблема:* Разработчик запускает тяжелый цикл на миллион итераций прямо внутри тела `new Promise`, ожидая, что этот код выполнится в фоновом потоке. В результате интерфейс приложения полностью замерзает.
    *   *Причина:* Исполнитель (executor) выполняется синхронно в основном потоке. Создание промиса не переносит код в фоновые потоки автоматически.
    *   *Решение:* Переносите тяжелые вычисления в Web Workers или разбивайте их на асинхронные микро-чанги через таймеры.
