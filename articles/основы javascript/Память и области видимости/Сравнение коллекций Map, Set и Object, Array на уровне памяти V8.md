# Сравнение коллекций Map/Set и Object/Array на уровне памяти V8

## БЫСТРЫЙ СТАРТ

*   **Обычные объекты (`{}`)** оптимизированы движком V8 для фиксированных структур данных с предсказуемыми ключами. Использование их в качестве динамических хэш-таблиц (кэшей) ломает оптимизацию скрытых классов и замедляет доступ к свойствам.
*   **Обычные массивы (`[]`)** эффективны для последовательного перебора, но проверка вхождения через `.includes()` требует линейного обхода $O(N)$ всех элементов.
*   **Коллекции `Map` и `Set`** — это специализированные нативные структуры хэш-таблиц. Поиск, добавление и удаление элементов в них выполняются за константное время $O(1)$, а ключами могут выступать любые типы данных, включая объекты и функции.
*   **Используйте Map/Set для:** динамических словарей, кэширования результатов по объектам-ключам, частых проверок вхождения в больших наборах данных.
*   **Используйте Object/Array для:** статических записей (DTO), сериализации в JSON и простых индексированных списков фиксированной длины.

## ПРАКТИЧЕСКИЕ ШАБЛОНЫ ДЛЯ КОПИРОВАНИЯ

### Шаблон 1: Высокопроизводительный динамический кэш на `Map` с ссылочными ключами
*   **Назначение:** Реализация кэша результатов выполнения тяжелых функций, где в качестве ключей выступают сложные объекты конфигураций.

```typescript
export interface Configuration {
  clientId: string;
  scope: string;
}

export interface MetricData {
  loadTimeMs: number;
}

export class MetricsCacheHolder {
  // Нативно связываем сложный объект-ссылку с его результатом.
  // Обычный объект { [key]: val } так сделать не позволит, так как преобразует ключ в "[object Object]"
  private readonly cache = new Map<Configuration, MetricData>();

  public save(config: Configuration, data: MetricData): void {
    this.cache.set(config, data); // Запись в хэш-таблицу выполняется за O(1)
  }

  public get(config: Configuration): MetricData | undefined {
    return this.cache.get(config); // Поиск выполняется мгновенно за O(1)
  }

  public clear(): void {
    this.cache.clear(); // Быстрый сброс всей структуры в оперативной памяти
  }
}
```

### Шаблон 2: Безопасный реестр метаданных без утечек памяти через `WeakMap`
*   **Назначение:** Ассоциация временных служебных данных с DOM-элементами или объектами сессии. Записи автоматически удаляются из памяти при уничтожении объектов-ключей.

```typescript
export interface ElementState {
  isRendered: boolean;
  clickCount: number;
}

export class DOMStateRegistry {
  // WeakMap удерживает ключи по "слабой" ссылке.
  // Как только HTMLElement будет удален из DOM-дерева и на него исчезнут внешние ссылки,
  // Garbage Collector сотрет запись из WeakMap автоматически.
  private readonly registry = new WeakMap<HTMLElement, ElementState>();

  public trackElement(element: HTMLElement): void {
    this.registry.set(element, {
      isRendered: true,
      clickCount: 0
    });
  }

  public incrementClick(element: HTMLElement): void {
    const currentState = this.registry.get(element);
    if (currentState) {
      currentState.clickCount += 1;
      this.registry.set(element, currentState);
    }
  }
}
```

### Шаблон 3: Мгновенная валидация уникального членства через `Set`
*   **Назначение:** Оптимизация ресурсоемких проверок прав доступа или ролей пользователей в больших массивах данных.

```typescript
export function filterAllowedResources(
  allResources: string[],
  userPermissions: string[]
): string[] {
  // Конвертируем массив разрешений в нативный Set.
  // Это преобразует линейный массив в быструю хэш-таблицу в оперативной памяти
  const permissionSet = new Set<string>(userPermissions);

  // Фильтруем исходный список
  return allResources.filter((resourceId) => {
    // Метод .has() отрабатывает за константное время O(1).
    // Если бы мы использовали userPermissions.includes(resourceId), сложность была бы O(N * M)
    return permissionSet.has(resourceId);
  });
}
```

## ГЛУБОКОЕ ПОГРУЖЕНИЕ

### 1. Как движок V8 оптимизирует объекты: Скрытые классы против Dictionary Mode
В оперативной памяти JavaScript-объект не хранится как простая хэш-таблица. Для оптимизации доступа JIT-компилятор движка V8 генерирует под каждый объект внутреннюю структуру — **Скрытый класс (Shape / Map)** [3].

1.  **Fast Properties (Быстрые свойства):**
    Если вы создаете объекты с одинаковой структурой ключей (например, экземпляры класса), V8 привязывает их к одному Скрытому классу. Свойства хранятся в линейном массиве, а доступ к ним по ключу превращается в быстрое смещение в памяти (Offset), минуя поиск по строке [3].
2.  **Dictionary Mode (Режим словаря / Медленные свойства):**
    Если вы начинаете использовать объект как динамический кэш — постоянно добавляете новые случайные ключи во время выполнения программы или удаляете их через `delete` — V8 понимает, что структура нестабильна. Он ломает Скрытый класс и переводит объект в "режим словаря" (хэш-таблицу на базе строк) [3]. Доступ к свойствам такого объекта замедляется в разы, а накладные расходы по памяти увеличиваются.

Коллекция `Map` изначально спроектирована как динамическая структура данных. V8 не пытается строить для нее скрытые классы, а оптимизирует ее на уровне системных C++ хэш-таблиц с предсказуемым потреблением ресурсов.

### 2. Алгоритмическая сложность и хэширование в Map/Set
Для небольших коллекций (до 30–50 элементов) разница в скорости поиска между массивом и хэш-таблицей Set незаметна. Но с ростом объема данных она становится критической.

*   **Массив (`includes` / `indexOf`):** Линейная сложность $O(N)$. С каждым новым элементом время проверки вхождения увеличивается пропорционально.
*   **Множество (`Set.prototype.has`):** Константная сложность $O(1)$. Поиск по хэш-коду ключа выполняется за фиксированное время, не зависящее от общего размера множества.

### 3. Физика сборщика мусора: WeakMap и WeakSet
Спецификация JavaScript не позволяет напрямую управлять памятью, но предоставляет инструменты для предотвращения утечек.

В обычном `Map` ключи удерживаются по **сильной ссылке (Strong Reference)**. Если вы используете объект (например, HTMLElement) в качестве ключа в `Map`, этот объект никогда не будет удален сборщиком мусора, даже если вы полностью вырежете его из DOM-дерева и занулите все переменные в программе — `Map` продолжает удерживать его в куче.

`WeakMap` и `WeakSet` решают эту проблему:
*   Ключами в `WeakMap` могут выступать **строго ссылочные типы данных (объекты, массивы, функции)**. Примитивы в качестве ключей запрещены.
*   Связь ключа с коллекцией является **слабой (Weak Reference)**. Она игнорируется алгоритмом Mark-and-Sweep сборщика мусора.
*   Как только объект-ключ уничтожается во внешней программе, сборщик мусора беспрепятственно стирает его из кучи вместе со связанным значением внутри `WeakMap` во время следующего цикла очистки [4].

### 4. Детальный пошаговый разбор автоматической очистки памяти в WeakMap
Разберем жизненный цикл `DOMStateRegistry` (Шаблон 2):
1.  **Регистрация элемента:** Вызывается `registry.trackElement(divElement)`. В `WeakMap` создается слабая связь: ключ `divElement` указывает на объект состояния `{ isRendered: true, clickCount: 0 }`.
2.  **Работа программы:** Элемент находится на экране, пользователь кликает, данные обновляются. Сборщик мусора обходит граф зависимостей. Объект `divElement` досягаем от глобального корня `document.body` $\rightarrow$ память не очищается.
3.  **Удаление элемента:** Выполняется `divElement.remove()`. Переменная, удерживающая ссылку в JS, очищается: `divElement = null`.
4.  **Сборка мусора:** Запускается цикл Garbage Collection. Сборщик мусора видит, что на объект в памяти больше не ведет ни одна сильная ссылка. Слабая ссылка из `WeakMap` им игнорируется. Объект `HTMLElement` признается недосягаемым, удаляется из памяти, а связанная с ним запись `{ isRendered: true, clickCount: 0 }` стирается из `WeakMap` автоматически без ручной очистки.

### 5. Типичные ошибки и их решение

*   **Ошибка 1: Утечка памяти при использовании сложных ключей в стандартном `Map`**
    *   *Проблема:* Приложение начинает потреблять всё больше оперативной памяти после длительной работы. Вкладка браузера замерзает или перезапускается.
    *   *Причина:* Использование стандартного `Map` для связывания метаданных с динамическими объектами (например, сессиями пользователей или DOM-компонентами). Объект удален из бизнес-логики, но ссылка внутри `Map` продолжает удерживать его в памяти.
    *   *Решение:* Заменяйте `Map` на `WeakMap` во всех сценариях, где время жизни ассоциативных данных должно быть жестко привязано к времени жизни самого объекта-ключа.

```typescript
// ПЛОХО (Удаленный объект user навечно зависнет в куче из-за сильной ссылки в Map)
const sessionCache = new Map<object, string>();
let user: object | null = { id: '1' };
sessionCache.set(user, 'active_session_token');
user = null; // Объект не будет очищен!

// ХОРОШО (WeakMap позволяет сборщику мусора очистить память)
const secureCache = new WeakMap<object, string>();
let sessionUser: object | null = { id: '2' };
secureCache.set(sessionUser, 'active_token');
sessionUser = null; // Память успешно освобождена автоматически
```

*   **Ошибка 2: Иллюзия использования объектов в качестве ключей в литералах `{}`**
    *   *Проблема:* Разработчик пытается использовать объект в качестве ключа в обычном `{}` и обнаруживает, что данные перезаписывают друг друга.
    *   *Причина:* Ключами в обычных объектах JavaScript могут быть только строки или символы (`Symbol`). При передаче объекта в качестве ключа (например, `obj[user] = 'data'`), JS неявно приводит его к строковому представлению, вызывая метод `.toString()`. Все объекты превращаются в одну и ту же строковую заглушку `"[object Object]"`, перезаписывая значения друг друга.
    *   *Решение:* Используйте только `Map` или `WeakMap`, если ключами должны выступать сложные объекты-ссылки.

```typescript
// ПЛОХО (Все записи перезапишут друг друга под единым строковым ключом)
const badStore: any = {};
const keyA = { id: 1 };
const keyB = { id: 2 };
badStore[keyA] = 'Value_A';
badStore[keyB] = 'Value_B'; // Перезапишет Value_A!
console.log(badStore[keyA]); // Выведет "Value_B" вместо "Value_A"
```

*   **Ошибка 3: Накладные расходы на частую конвертацию массивов в `Set`**
    *   *Проблема:* Код фильтрации начинает работать медленнее после рефакторинга с переходом на `Set`.
    *   *Причина:* Конвертация массива в `Set` (вызов `new Set(array)`) — это линейная операция $O(N)$, требующая выделения памяти под хэш-таблицу. Если выполнять эту конвертацию на каждой итерации внешнего тяжелого цикла, накладные расходы на пересоздание `Set` полностью нивелируют выгоду от быстрого поиска за $O(1)$.
    *   *Решение:* Создавайте коллекцию `Set` один раз заранее, вне тела циклов или тяжелых итерационных методов.

```typescript
// ПЛОХО (Set пересоздается в памяти 1000 раз, уничтожая производительность)
function processBatchUnsafe(users: string[], allowed: string[]) {
  return users.filter(user => new Set(allowed).has(user)); // ! Катастрофа производительности
}

// ХОРОШО (Set создан один раз, поиск внутри фильтрации идеален по скорости)
function processBatchSafe(users: string[], allowed: string[]) {
  const allowedSet = new Set(allowed); // Создан один раз вне цикла
  return users.filter(user => allowedSet.has(user));
}
```
